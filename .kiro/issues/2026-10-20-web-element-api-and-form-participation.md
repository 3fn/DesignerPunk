## E1. Input-Checkbox-Base violates its own required `validation_form_integration` contract on web (P0)

- **The contract**: `src/components/core/Input-Checkbox-Base/contracts.yaml:143–161` reads "Checkbox participates in native form submission. Value is included in form data when checked." It is `required: true` with `platforms: [web, ios, android]`. Input-Checkbox-Legal inherits it (`Input-Checkbox-Legal/contracts.yaml:4`, `inherits: Input-Checkbox-Base`). Both READMEs repeat the claim (`Input-Checkbox-Base/README.md:46`, `Input-Checkbox-Legal/README.md:106`).
- **The element**: the native `<input type="checkbox" name=…>` is rendered **inside the shadow root** (`Input-Checkbox-Base/platforms/web/InputCheckboxBase.web.ts:103` `attachShadow`, `:457` `name`, `:474` `type="checkbox"`). The element is not form-associated: no `static formAssociated`, no `attachInternals`, no `setFormValue`. Across all 34 web components, only `Input-Radio-Base/platforms/web/InputRadioBase.web.ts:83` (`formAssociated = true`) and `:121` (`attachInternals()`) are. Legal also renders in its own shadow root (`InputCheckboxLegal.web.ts:88`).
- **What does work**: form **reset**. It is wired by hand: a listener on the closest ancestor form (`InputCheckboxBase.web.ts:341–343`, `:353–355`), tested at `__tests__/InputCheckboxBase.test.ts:482–512`.
- **REASONING**: a form owns only controls in its own tree, so a checkbox inside a shadow root is not in the outer form's `FormData` or submission. This needs a real browser to confirm (see E7).
- **Fix shape (Lina's read; the fix PR decides)**: make the element form-associated with `ElementInternals` (`setFormValue` on check/uncheck, plus `formResetCallback`, which replaces the hand-wired listener). This is additive, so it need not wait for a major. The alternative, narrowing the contract to exclude web, would make the contract match by giving up the behaviour. That is a contract change, and it is Peter's call if it is ever proposed.
- **Not verified**: what "native form submission" means on iOS and Android. Neither platform has an HTML form, and this record does not examine the native implementations.

## E3. Input-Text-Base rebuilds its shadow DOM on `error-message` and `is-success`

- `InputTextBase.web.ts:189–218`: a `value` change updates the inner input directly and returns early (`:192–199`). A change to `error-message` (`:200`) or `is-success` (`:207`) falls through to `render()` (`:216–217`). `render()` rebuilds the container through `innerHTML` (`:288`), then clears and refills the shadow root (`:329` `this._shadowRoot.innerHTML = ''`).
- **REASONING (needs a real browser)**: replacing the `<input>` drops focus and caret, so live validation while the user types loses their place.

## E6. NavSegmentedChoice's `aria-controls` cannot reach its panels

- The element renders in an open shadow root (`NavSegmentedChoiceBase.web.ts:81`). Each segment gets `aria-controls="${id}-panel-${value}"` (`:262–266`), and the panels belong to the adopter, outside the shadow root. The contract is `accessibility_aria_controls`, `required: true` (`Nav-SegmentedChoice-Base/contracts.yaml:352–366`).
- **REASONING**: ID references do not cross a shadow root, so the reference resolves to nothing. ARIA reference-target support, which could change this, is **UNVERIFIED**. The contract's own validation (`:362–363`) checks only that the attribute is present, so it passes against a reference that resolves to nothing. That is a guard weaker than its claim.
- **2026-10-25 (Lina, owner): E6 RESOLVED-pending-merge** on branch `fix/release-16.1.0-floor-lina`, in the commit that adds this line, and pending Sparky's browser line. Authority: Peter, 2026-10-25, in chat, relayed verbatim by the orchestrator: "Fix all of them as the owners recommend; T is (A)". At the release 16.1.0 walk (Floor batch line E6) that took up Stacy's F-B reading (E6 floor-class) and adopted my fix-now, "with the narrowed-contract fallback text if it is not browser-verified by S".
  - **The premise, now VERIFIED** against the HTML spec text (html.spec.whatwg.org, "Reflecting content attributes in IDL attributes", fetched and read 2026-10-25). An ID in the content attribute is looked up among elements whose "root is the same as element's root", so the bare attribute in the shadow root resolves to nothing. That is Stacy's spec fact. An element reference set through the `FrozenArray<T>?` setter is returned when it "is a descendant of any of element's shadow-including ancestors", so it may point outward into the host's tree. The setter sets the content attribute to the empty string, and a later change to the attribute clears the reference.
  - **Fix.** `NavSegmentedChoiceBase.web.ts` `_resolvePanelReferences()`: for each segment, look up `[id]-panel-[value]` in `this.getRootNode()` (the adopter's tree: the document or an enclosing shadow root), and set `ariaControlsElements = [panel]` where the browser has it. A `MutationObserver` on that root (child list and `id` attributes, while `id` is set and the API exists, disconnected on disconnect) keeps the reference current when panels are added, removed or replaced later. Where no panel exists, or the browser lacks `ariaControlsElements`, the `[id]-panel-[value]` attribute stays as the fallback. A change to `id` re-renders.
  - **Contract.** `accessibility_aria_controls` validation went from "aria-controls follows [id]-panel-[value] pattern" (attribute present) to "the reference resolves to the element with id [id]-panel-[value] in the adopter's tree, when it exists". I added "never to another element", and the behaviour line states the web mechanism. The promise is not narrowed. The web limit for a browser without `ariaControlsElements` is stated in the README, not the contract (see the residual).
  - **Tests.** `NavSegmentedChoiceBase.ariaControls.test.ts`, 13 tests. jsdom 26 has no `ariaControlsElements`, so the tests install a test double that follows the spec algorithm quoted above. They cover: the bare attribute resolving to nothing across the shadow root; panels in the document; a missing panel never resolving to another element; panels added after render, replaced, removed, and given their `id` later; an enclosing shadow root resolving in that tree and not to a same-id decoy in the document; `id` changes, both paths; no `id`; the observer stopped on disconnect; the fallback with no API. Suite: 5 suites, 125 tests pass. Mutation check: five mutations (look up in `document`, not the root; no observer; no attribute fallback; no resolve; no `id` re-render), and each turns tests red.
  - **What is verified, and what is not.** The mechanism is VERIFIED by the spec text plus the jsdom double. These are **UNVERIFIED** until Sparky's run: that a real browser implements the setter as specified; that it exposes the relation to assistive technology (Chromium DevTools, Accessibility pane, "Controls"); and which browsers have the API (REASONING, from memory and not checked: Chromium 135+, Firefox 136+, Safari has some element reflection).
