None of these is a token-name error, so the normalization PR does not fix them. Each is a place where what a component reads, or whether its code is valid, is in question. They are listed so none is lost (rule 10).

1. **Input-Text success border reads a text token.** `InputTextBase.web.css` L127–128 draws the success border with `--color-feedback-success-text` (green500). `color.feedback.success.border` (green400) exists, and Input-Checkbox uses `color.feedback.error.border`. The success value differs, so a change is visible, not a no-op. The error border has the same shape (`error.text` and `error.border` are both pink400, so only the success side changes colour). **Fork for Peter or the design owner**: keep the text token as a deliberate choice, or move the border to `*.border`. Until ruled, the Input-Text schemas declare `color.feedback.success.text` and `color.feedback.error.text`, which is what is read.
2. **Button-CTA typography differs across platforms.** Android reads `typography.buttonMd` and `typography.buttonLg` (`ButtonCTA.android.kt` L278–300); web and iOS read `typography.labelMd` and `typography.labelLg`. The schema now declares all four, so each declaration is true for one platform and the parity gap is visible there. **Owner question**: which pair is canonical. Stacy is asked to read this as a cross-platform parity finding. The small size has no declaration of its own: Android uses `buttonMd`, web and iOS `labelMd`.
3. **`InputTextBase.android.kt` L466–473 likely does not compile.** The block declares uninitialised `private val colorBorder: Color` and `colorBackground: Color`, and `private const val ...: Float` typography constants, each with a `// Generated from color.border` style comment. `color.border` and `color.background` are retired names (both now `color.structure.*`). Kotlin rejects a `val` with no initializer at top level, so I expect a compile error; I have not built it. **Probe**: build the Android target, or let the Spec 129 build-verification harness do so. If it fails, re-class this record P1 consumer-blocking and fix first.
4. **94 tokens that web code reads are still undeclared after the normalization.** After the pass every declared name resolves (513 declarations, 0 unresolved) but the declarations are not complete: Button-CTA reads `shadow.hover`, `radius200`, `tapAreaMinimum`, `space.inset.300` and `space.inset.400` without declaring them; Input-Checkbox reads `labelLg` and `caption`. The count is Ada's (drift ruling L-5), from a script that maps each `var(--…)` in `platforms/web/**` back to its token-index key; it was not recomputed here and must be re-run before anyone acts on the number. Consequence: `get_token_consumers` still omits those consumers. **Fix shape**: either add them to the schemas in a pass, or build the declared-versus-read instrument Ada offered (extending `StemmaTokenUsageValidator.validateAgainstSchema`, which today matches by substring) so the gap is caught by a guard rather than a review. The class option is the instrument.
   *(Added 2026-10-23, Lina, from the guard read.)* Two surfaces the token-name guard does not read belong here too. The three Badge schemas (Badge-Count-Base, Badge-Count-Notification, Badge-Label-Base) have no `tokens:` key at all, so no Badge component is a consumer of anything. Container-Card-Base's `default_tokens:` map names `radius.normal`, which its `tokens:` does not declare (all eight `default_tokens` names resolve).
5. **Android Button-CTA and Avatar assign sizing primitives, which are `Float`, to `Dp` fields.** *(Added 2026-10-23, Lina, found while pointing Button-CTA's web and iOS minimum widths at the primitives Android reads.)* The generated `DesignTokens.android.kt` emits sizing as `const val size_700: Float = 56f`, while spacing and radius are `Dp` (`val space_200 = 16.dp`). `ButtonCTA.android.kt` L276–304 passes `DesignTokens.size_500/600/700/900/1000` straight into `ButtonCTASizeConfig`'s `Dp` fields (`height`, `minWidth`, and large's `touchTargetHeight`), and `Avatar.android.kt` L222–247 does the same for `dimension: Dp` (all six sizes). Kotlin has no implicit Float-to-Dp conversion, so I expect both files not to compile. Progress-Bar-Base and Nav-TabBar-Base read the same `Float` primitives correctly, with `.dp` at the use site. I have not built it. **Probe**: the same as item 3. **Fix shape** if it fails: `.dp` at each read (component side, mine). Whether sizing should be emitted as `Dp` like spacing is Ada's question about the Android generator, not a fix this record makes.

6. **Inheriting variants restate their parent's tokens, against the own-tokens-only schema rule.** *(Added 2026-10-23, Lina, from the guard read.)* My charter's schema rule says a schema lists only the tokens its own code reads; inherited and composed tokens are assembled by the MCP. Five of the nine inheriting schemas restate the parent's whole list instead:
   - Input-Text-Email, -Password and -PhoneNumber restate Input-Text-Base's 23, unlabelled.
   - Chip-Filter and Chip-Input restate Chip-Base's 18 under `inherited:`. Both lists equal the base today.

   The variants do read those variables at runtime; Chip-Filter imports `ChipBase.styles.css` into its own shadow root. So the restated edges are true, but they are hand copies that will drift. The drift record's Outcome claim that `color.feedback.success.text` lists the four Input-Text components rests on three of them. Composition was settled the other way: Nav-Header-Page's `composition:` group was deleted (F-2). **Fork for Peter** (Ada consulted, because one branch changes her generator):
   - **(i) Keep the restatements.** Amend the charter rule to say a variant restates what it renders (a `canonical/agents/lina.md` edit, Peter-merged), and guard each copy against its parent.
   - **(ii) Derive the edges.** The consumer map and the MCP's `resolvedTokens` derive inheritance (and composition) edges from `inherits:` and `composition:`, and the restatements are deleted.

   **Class option: (ii).** Surviving counter-argument: a derived edge means "affected by", not "reads", and that widens what `consumers` means. Until ruled, nothing changes.
