## What is wrong

Read at `bdbe72a32`.

1. **The file.** `src/components/core/Badge-Count-Notification/tokens.ts` has no `defineComponentTokens` call. The only two occurrences of the string in the component directory are in its comments (`tokens.ts` L14 and L38, both saying the API "only supports numeric values"). It exports `BadgeNotificationColorTokens` (L54), a plain map of two semantic-token names (`notification.background` to `color.feedback.notification.background`, `notification.text` to `color.feedback.notification.text`), plus a key type (L78) and an accessor (L95). That is a legitimate colour-reference map, the architecture Spec 058/059 chose for colour (the file's own header, L1 to L30). It is not a bug in the map.

2. **The loader's name rule.** `src/cli/loadComponentTokens.ts` `isTokenFileName` (L163 to L165) returns true for the basename `tokens.ts` and for any basename ending `.tokens.ts`. Source 1 adds every such file to `scannedTokenFiles` (L95), and the Source 2 scan, `scanForTokenFiles` (called at L104, adding at L246), does the same. `designerpunk.config.ts` L22 to L25 lists `./src/components/core` among `componentTokens` directories, so the loader scans this file in-repo. At L120 to L124 the harvest-zero lint warns (L122) for any scanned file with zero branded exports, printing `harvestZeroWarning(file)` (defined L178 to L180): "this scanned file harvested zero component tokens; if you meant to register values, call `defineComponentTokens`."

3. **The six real token files against this one.** `git grep -n 'defineComponentTokens(' src/components/core/*/tokens.ts src/components/core/*/*.tokens.ts` at `bdbe72a32` matches in six files, each with a real call: `Avatar-Base/avatar.tokens.ts` (3 matches), `Badge-Label-Base/tokens.ts` (2), `Button-Icon/buttonIcon.tokens.ts` (4), `Button-VerticalList-Item/Button-VerticalList-Item.tokens.ts` (2), `Input-Checkbox-Base/checkbox-sizing.tokens.ts` (1), `Input-Radio-Base/radio-sizing.tokens.ts` (1). The seventh file the pattern matches, `Badge-Count-Notification/tokens.ts`, matches twice and both are comments. So six of seven call it. (This is the false claim the sibling record's L15 made, corrected there by a dated line in the same PR.)

4. **The warning.** By reading the code above, an in-repo `generate` prints the harvest-zero warning naming this file. **Not observed:** I derived this from the loader and the config and did not run `generate` for this record. The orchestrator's consult reported the warning as firing; the first step of the fix PR is to run `generate` before and after and quote both outputs.

- **Update `Badge-Count-Notification/index.ts`**: the import at L44 (`from './tokens'`), the `@see ./tokens.ts` at L25, the prose at L20 to L22 (which says Rosetta "mandates component tokens live at `src/components/[ComponentName]/tokens.ts`", a claim the six real files contradict by name), and the three `generated by the token build pipeline from tokens.ts` comments (L56, L58, L60).

## Why it is a record and not a fix in the PR that found it

It was found during a consult on the guard's build, which is Thurgood's instrument under a grant limited to `scripts/governance-examples/**`; the rename touches component source and Ada's tests, outside that grant and outside a record-only PR. Rule 10 asks for the obligation to be filed in the PR that records it.

**Surviving counter-argument**: the cheaper alternative is to leave the name and narrow the lint (teach the loader that a `tokens.ts` whose exports are all semantic-reference strings is acceptable), which touches one file instead of eleven. I weigh it down because the loader's comments (L156 to L161; and L112 to L118, which calls such a file one that "very likely wears the wrong filename") say the name convention is deliberately the lint's target, and a name that matches the convention while meaning the opposite is the confusion the lint exists to catch; and a lint exemption by file content is a second detection mechanism, which the loader's own comment (L112 to L118, citing Spec 123 Req 8.2) rules out. The survivor: the rename touches platform files on three platforms for a comment-level change, and Peter may prefer the exemption. That is his pick.

**Unchecked here**: the proposed new basename; whether any consumer repo imports `@3fn/core` component source by the `tokens` path (the `index.ts` re-export keeps the public names, but a deep import of the file by path would break; the fix PR greps the shipped `dist` and the package `exports` first).
