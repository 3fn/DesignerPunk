# `scripts/generate-token-index.ts` Uses the Pre-117-Task-3 `TokenIndexInput` API (TS2353; standalone token-index regen broken)

**Date**: 2026-06-24
**Discovered during**: Spec 118 Increment-1 ambient-loader regression fix — unmasked once `npm run build` proceeded past the prebuild loader failure that had been aborting earlier
**Reporters**: Thurgood (triage), Ada/Lina (corroboration)
**Severity**: Medium — the standalone token-index regeneration script cannot compile/run; non-blocking in `npm run build` (logged and skipped, build exits 0), so the committed `token-index/` is silently NOT regenerated by this path
**Type**: Token-index / stale caller of a refactored API
**Primary owner**: Ada (Rosetta token pipeline) — Spec 117 Task 3 follow-up
**Status**: ✅ RESOLVED (2026-06-24, `spec-118-module-resolution-coherence` branch) — see § Resolution. The standalone divergent script was *retired*, not patched; the build now generates the token-index from the same shared source as the CLI.

---

## Summary

Spec 117 Task 3 refactored `generateTokenIndex`'s input type. `TokenIndexInput` (`src/generators/generateTokenIndex.ts:27-35`) now requires a single `modeResolved: ModeResolvedTokens` object — its doc comment: *"The single shared mode-resolved truth from `generateTokenFiles` (Spec 117 Task 3). Carries the base-scoped theme-varying set AND per-primitive mode-resolved OKLCH…"* — and the implementation reads `input.modeResolved.themeVaryingTokens` (`:113`).

But the standalone regen script `scripts/generate-token-index.ts:39-44` still calls it with the **old shape**:

```ts
generateTokenIndex(OUTPUT_DIR, {
  primitiveTokens: getAllPrimitiveTokens(),
  semanticTokens: getAllSemanticTokens(),
  componentTokens: ComponentTokenRegistry.getAll(),
  themeVaryingTokens,          // ← old top-level field; no longer in TokenIndexInput
});                            //    (and the now-required `modeResolved` is missing)
```

→ `scripts/generate-token-index.ts(43,3): error TS2353: ... 'themeVaryingTokens' does not exist in type 'TokenIndexInput'`.

## Impact

- `npx ts-node scripts/generate-token-index.ts` fails to compile → the **standalone token-index regeneration entry point is broken.**
- In `npm run build`, this runs as a sub-step of `generate-platform-tokens.ts` and is caught/logged as *"Token index generation failed (non-blocking)"* — the build still exits 0, but the `token-index/` artifacts are not refreshed by this path.
- The **main generate path is unaffected**: `generateTokenFiles` calls `generateTokenIndex` with the new `modeResolved` shape, so the documented consumer `generate` works (verified — 217 tokens, token-index produced in the consumer project).

## Why it surfaced now

It was masked by the Spec 118 Increment-1 prebuild regression (the build died earlier, in `generate-platform-tokens.ts`'s `loadConfig`). Fixing that regression let the build reach this step and expose the long-standing stale call.

## Why out of scope for Spec 118

Spec 118 is module-resolution coherence. This is a token-index API-currency defect (a stale caller of a Spec-117-Task-3 refactor) — no module-resolution dimension.

## Recommended disposition

Ada (or whoever owns the parked Spec 117 token-index work) to update `scripts/generate-token-index.ts` to construct the shared `ModeResolvedTokens` (the same mode-resolved truth `generateTokenFiles` builds) and pass `modeResolved` instead of the top-level `themeVaryingTokens`. Acceptance: `npx ts-node scripts/generate-token-index.ts` compiles and regenerates `token-index/` correctly; the "non-blocking" warning disappears from `npm run build`.

---

## Resolution (2026-06-24)

Rather than patch the standalone script (which would have preserved a second, divergent index-generation path — the very thing Spec 117 Task 3 exists to eliminate), the **divergent path was retired**:

- **`scripts/generate-token-index.ts` deleted.** Its only caller was `generate-platform-tokens.ts`'s `execSync` shell-out.
- **`scripts/generate-platform-tokens.ts` now generates the token-index INLINE** from the `ModeResolvedTokens` returned by the `generateTokenFiles` call it already makes — one shared source for both the platform files and the index, so they cannot drift. Blocking (a failed/stale index fails the build).
- **Two divergences the standalone script carried are eliminated, not reproduced:** (1) it computed `themeRegistry.getThemeVaryingTokens()` = the stale registry-wide **10** (the bug Task 3 §4.1 fixed) — the inline path uses the base-scoped **5** off `modeResolved`; (2) it populated the component registry from a **hardcoded 5-import subset** (27 tokens) — the build now uses `loadComponentTokens(config)` source-presence discovery (Task 4 / R4) → all **33** (incl. the recovered inputcheckbox/inputradio sizing).

**Verified:** `npm run build` exits 0; `git diff token-index/` is **empty** (the build reproduces the committed-correct index exactly: 33 components, 5 theme-varying, 16 shadow-rgba); full `npm test` 8969 green; `tsc` clean. (Build runs green because it's on the branch carrying Spec 118's Increment-1 ambient-loader fix.)

**Root cause of the gap (process):** Spec 117 Task 3 changed `TokenIndexInput`, but `scripts/**` is excluded from `tsconfig.json` (`include: ["src/**/*"]`), so the main-loop `tsc --noEmit` never typechecked this caller — it only fails when ts-node runs it (the build), which the 118 prebuild regression had been masking. The standalone script + `generate-platform-tokens.ts` were also a parallel reimplementation of `runGenerate`'s path, which is how they drifted.
