# @3fn/core Feedback — Ada (Rosetta Token Specialist)

**Date**: 2026-05-09
**Context**: First implementation task on a product repo consuming `@3fn/core@11.1.5`
**Agent**: Ada — token development, pipeline integration

## 1. Pipeline Source Resolution Is Invisible

**Issue**: When running `npx designerpunk generate`, there's no indication of *where* the pipeline is reading token definitions from. The output shows the config file path and output directory, but not the token source path.

**Impact**: I edited `src/tokens/FontFamilyTokens.ts` (local source), ran the pipeline, and got stale output. It took investigation to discover the pipeline reads from `node_modules/@3fn/core/src/tokens/`, not from the local copy.

**Suggestion**: Add a line to the pipeline's startup output:

```
📦 DP-Portfolio (DPP)
   Source: /path/to/project
   Tokens: /path/to/node_modules/@3fn/core/src/tokens  ← ADD THIS
   Output: /path/to/dist/tokens
   Themes: wcag (light)
```

This makes the data flow explicit. An agent or developer immediately sees where tokens are being read from and knows which file to edit.

---

## 2. Dual-Edit Requirement Is Undocumented

**Issue**: Product repos that maintain a local `src/tokens/` (for contribution back to core) must edit *both* the local source AND `node_modules/@3fn/core/src/tokens/` for changes to take effect in the pipeline immediately. This isn't documented anywhere.

**Impact**: The first edit appeared to do nothing. The workaround (editing node_modules) feels wrong — it's fragile (lost on `npm install`) and non-obvious.

**Suggestion**: Either:
- **Option A**: Document the dual-edit workflow in the Integration Guide or README. "During development, edits to `src/tokens/` require a corresponding edit to `node_modules/@3fn/core/src/tokens/` until the next publish."
- **Option B** (better): Add a `tokenSource` config option to `defineConfig()` that lets products point the pipeline at their local `src/tokens/` instead of the package. This eliminates the dual-edit entirely:

```typescript
export default defineConfig({
  name: 'DP-Portfolio',
  tokenSource: './src/tokens',  // ← Use local source instead of package
  output: './dist/tokens',
});
```

Option B would also make the "source mode" consumption model explicit in the config, which addresses the framing confusion from the 2026-05-08 lessons learned.

## 3. Font Family Tokens Are Categorical but Use Numeric Interface

**Minor**: Font family tokens use `baseValue: 0` and `mathematicalRelationship: 'N/A - Categorical value'` because the `PrimitiveToken` interface requires numeric fields. This works but feels like the interface wasn't designed for categorical tokens.

**Not blocking** — just noting that if the interface ever gets a revision, categorical tokens (font families, easing curves) might benefit from a distinct type that doesn't require dummy numeric fields.

## 4. No Way to Run Token Tests from Product Repos

**Issue**: Token unit tests (`FontFamilyTokens.test.ts`, etc.) exist in `@3fn/core` but cannot be run from a product repo. Jest ignores `node_modules/` by default, and the product repo has no test runner configured. After editing token primitives, the only validation available is the pipeline's built-in checks (semantic validation, cross-platform consistency) and manual output inspection.

**Impact**: Can't verify that token mathematical relationships, naming conventions, or family constraints still hold after edits. The pipeline validates generation but not the token definitions themselves (e.g., it won't catch a font family token with a missing fallback stack or a spacing token that breaks baseline grid alignment).

**Suggestion**: Either:
- **Option A**: Ship a `npx designerpunk test` CLI command that runs the core token test suite against the active token source (whether package or local via `tokenSource` config). This would complement `npx designerpunk generate` as a validation step.
- **Option B**: Document how to configure Jest in a product repo to include `node_modules/@3fn/core/src/tokens/__tests__/` in the test paths.
- **Option C**: Include a lightweight validation script in the pipeline that checks token invariants (mathematical relationships, naming, required fields) as part of `npx designerpunk generate --validate`.
