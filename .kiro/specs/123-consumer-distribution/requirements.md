### THE MODEL B IDENTITY STATEMENT — the thesis every requirement derives from

*Ruled by Peter in the 2026-09-26 definitional dialogue. Recorded verbatim in substance. It is placed first because the requirements phase proved what happens when it lives only in scattered vision phrasings: the author derived a token decision from Q6 without it, and that derivation produced a consumer who could not author a single colour of their own.*

> **DesignerPunk is an ENGINE that births and then continuously runs a design system that is the CONSUMER'S OWN.** It is **not a design language consumers adopt** — the Material model was considered and **declined**.
>
> **Two postures:**
>
> - **`npm install` alone = CONSUME.** Reference corpus, library use, evaluation. DesignerPunk stays **ours**, read-only.
> - **install + `init` = BECOME.** **`init` is the BIRTH EVENT, run once per design system, ever.** The consumer's language is **theirs from the first commit**. **Ours stops flowing the moment it becomes theirs — by definition, not as a cost.**

**How to read the rest of this document against it:**

1. **Anything that is the consumer's LANGUAGE is theirs wholesale from birth**, and no mechanism keeps ours live underneath it. **Their token tier is their language** (Requirement 19A).
2. **Anything that is our UPDATING SURFACE is consumed by name and keeps flowing.** **Components are our updating surface** — consumed by name, merged with theirs, updated on `npm update` (Requirement 2).
3. **The one real residual coupling between the two is the NAME CONTRACT**: our updated components may reference a semantic token name their language does not have. `sync` reports it (Requirement 5A). That is the only place ours reaches into theirs, and it reaches by *reporting*, never by *writing*.
4. **The CONSUME posture is the reference-corpus mode** (R1's named secondary) plus library use and evaluation — which is why the § 8 probe ran the **no-init path** and why the install doc documents it (Requirement 15.3).
5. **A mechanism that keeps our base live under their language is a MODEL-A feature.** It is not a gap in this spec; it is the thing this spec's thesis declines. The token union is the recorded instance (Requirement 19A.F).

**User Story**: As a founder who has run `init`, I want to author my own tokens, themes and component tokens in a tree that is mine from birth, and to know which surfaces still come from the package, so that my design system is my language rather than DesignerPunk's palette wearing my components. *Traces: outline § 4.2, § 3.8 (R7 → Q6 ruled); Ada B1, Ada R1 Q6 position; Ada R2 item 2; **Peter, 2026-09-26 (Model B; token fork Option 1)**.*

> **R3 RE-DISPOSITION — stated rather than smoothed.** R2 derived from Q6 (package-primary) that the consumer's token authoring should resolve against the package. **Ada's R2 measurement showed where that derivation leads**: in package mode *"a consumer cannot introduce a single new colour value… Their 'design system' is DesignerPunk's palette wearing their components."* **Peter's Model B ruling locates the error in the premise, not the arithmetic**: package-primary governs our **updating surface** (components, consumed by name), not the consumer's **language** (tokens, theirs from birth). Three R2 dispositions reverse as a consequence — **1.2(i) `tokenSource` STAYS; 1.2(ii)+(iii) theme imports STAY LOCAL; 1.1's export subpath is no longer a precondition on the default path.** They are marked in place below.

### Requirement 2: Component catalog merges, never replaces (Q6 condition — Lina, Leonardo)

**User Story**: As a consumer authoring my first component, I want my component to appear **alongside** the ecosystem's components rather than replacing them, so that my most predictable first action does not silently delete my component library. *Traces: outline § 4.2; Lina B2 (blocking), Leonardo A14; Peter, 2026-09-26 (Model B).*

> **WHY COMPONENTS MERGE WHILE TOKENS ARE COPIED — the two tiers deliberately differ, and the reason is the identity statement.** **Components are our UPDATING SURFACE**: the consumer uses them **by name**, they improve on `npm update`, and a consumer who forks one does so by dropping their version in to win on its name. **Tokens are the consumer's LANGUAGE**: theirs wholesale from `init`, with nothing of ours running underneath (Requirement 19A). **A union at the component tier is the Model B answer; a union at the token tier would be the Model A answer, and it is declined.** A reader who sees the asymmetry as an inconsistency has read the mechanisms without the thesis.

#### Acceptance Criteria

1. The consumer-owned component root SHALL resolve as **union-with-precedence**: package components ∪ consumer components, with the consumer winning on name collision. It SHALL NOT resolve as first-non-empty-wins.
   - **The union SHALL apply to the resolved root SET INCLUDING THE ENV-SUPPLIED ROOT.** *(Lina R2 L-B1, blocking: `resolveConsumerOwnedRoot` returns on `envValue` **unconditionally**, with no existence check and no package fallback, and `init` **always** writes `COMPONENTS_DIR`. A union implemented in the cwd branch is dead code that no deployed consumer's process ever evaluates.)* **Env names the consumer's root; it does not name the only root.**
   - **Measured consequence this corrects, which is worse than the shadowing originally filed**: with the env var always set and the copy removed, the consumer's path does not exist, the env branch returns it anyway, and **the catalog is zero from minute one, before they author anything** — reported `healthy`.
   - Requirement 2 SHALL state **whether union semantics apply to all consumer-owned roots or to the component root only.** *(Lina R2 A8: the resolver also serves `tokenIndex` and the product server's roots, and the servers consume it through an **unchecked `as` cast against a hand-written interface** — so a return-shape change that misses one declaration site compiles clean and fails at runtime as a zero-component catalog reported healthy. Because the infra-ring consolidation is out of scope, this lands in three declaration sites, and that interaction is named here rather than discovered.)*
1a. **Launch-path values for this root are decided at Requirement 19A.5a; the union applies on BOTH launch paths.** *(⟲ Reduced to a cross-reference at the R3 confirm, on Lina's measured recommendation. The R3 text put a cross-tier policy clause here and it produced two defects in one round: **(i)** it did not repair the CLI path — the runner supplies `pkgRoot` **as the value** of a consumer-owned root, so a fixed resolver computes *union(package, package) = package* and the consumer's components are still never seen; that is a **value** defect, and values are decided at 19A; **(ii)** read literally it applied *"the policy this requirement specifies"* — the component **union** — to the **token index**, which is the Model-A union 19A.8 declines. **One pronoun flattened the asymmetry the banner above states on purpose.**)*
   - **FOR A READER OF REQUIREMENT 2 ALONE, stated so the split does not hide it** *(Lina's own surviving counter to her move: a Req-2-only reader loses sight of the CLI path)*: **the component catalog is served by TWO launch paths** — the scaffolded MCP config **and** the CLI runner (`mcp-app`, `mcp-product`) — and **the CLI runner currently defeats this requirement on its own** by hardcoding the package path as the component root's value. **Both paths, both server key names (`COMPONENTS_DIR` on the application server, `COMPONENT_DIR` on the product server), and the precedence rule are decided at 19A.5a.**
2. WHEN a consumer's component directory is **empty OR ABSENT** THEN the catalog SHALL present the full ecosystem component set. *(Leonardo R2 A2 — under a stopped copy the scaffolded value is **absent**, not empty; Lina R2 confirms both resolve identically today only in the branches the env short-circuit prevents from running.)* WHEN the consumer adds one component THEN the catalog SHALL present the ecosystem set **plus** that component — never that component alone.
3. The scaffolded `COMPONENTS_DIR` SHALL NOT resolve to a location that produces a **silently empty** catalog under package-primary, **and Requirement 19A SHALL name what the scaffolded value becomes.** *(Leonardo R2 A2: 2.3 forbade the outcome and named no positive resolution.)* *Traces: Leonardo A14 — "every screen-specification workflow dies quietly with a healthy-looking index."*
4. Requirement 2.1 SHALL land **before U2 or U3 depend on the catalog's contents.**
5. The per-component ownership path SHALL be this merge, not a command: **a consumer drops their fork in and it wins on its name; everything else continues to come from the package.** The install doc SHALL present this as the *first* ownership answer, with the repo clone as the whole-system escalation (Requirement 15.6). *Traces: Lina R1 Q6 — this answers § 14's "fork one component rather than the system" better than the retired `eject` would have.*
   - **The clone hatch, RE-ANCHORED to Model B** *(Leonardo R3 A21)*: under Model B, **`init` already makes the language yours**. **The clone gets you the ENGINE and the COMPONENTS** — DesignerPunk's own source, to own and change. It SHALL NOT be phrased as the way to *really* own your design system, because that tells the founder `init` does not make it theirs — the opposite of 15B.2, on two surfaces 15B.5 requires to agree.

### Requirement 4: The packaging floor is a decision, and it is pinned

**User Story**: As a consumer's agent reasoning about an installed package, I want the package to contain what consumption needs and not the material that only DesignerPunk's own development needs, so that I reason past less irrelevant surface — without any load-bearing asset silently disappearing. *Traces: outline § 6.4; Ada B3 (blocking), Ada A3, Lina B1 (blocking), Lina R2 § 1.*

#### Acceptance Criteria

1. The floor SHALL be **decided downstream of `init`'s copy decisions and the authoring surfaces (Requirements 19A, 1), not discovered by measurement.** *(Under Model B the package ships `src/tokens/**` **as `init`'s copy source** — the BECOME consumer's token tier is born from it — so the floor now guards the completeness of what is copied, not only of what package mode loads.)* *Traces: Ada B3 — "measurement tells you what resolves today, and today everything resolves because `init` copies."*
2. **The floor IS THE RUNTIME-RESOLUTION CLOSURE of the token tree `init` copies and of the package's runtime surfaces, derived mechanically. The bullets below are the DECLARED members; the closure is the COMPLETE one.** *(Ada R2 B1, blocking: `src/tokens/**` is loaded as raw TS at generate-time, so its runtime import closure is on the floor with it — and the escaping value-position imports include `TokenCategory`, an **`enum`, a runtime value**, which transpilation does not erase. ### Requirement 5A: The name-contract check — the one residual coupling under Model B

**User Story**: As a consumer whose design system is my own, I want to be told when an updated DesignerPunk component expects a token name my language does not have, so that `npm update` never silently breaks a component that used to render. *Traces: **Peter, 2026-09-26 (Model B; token fork Option 1)**.*
