# Task 1.5 Completion — `generate`: `token-index/meta.json` `tierDir`; theme readers use the recorded tier; write side anchored; the refusals; `figma-*` anchored

**Spec**: 123 — Consumer Distribution · **Unit**: U1 · **Parent**: Task 1 · **Agent**: Ada (Sonnet)

## What changed

### `token-index/meta.json` + the theme readers follow it (DD24)

- `src/generators/generateTokenIndex.ts`: `TokenIndexInput` gained `tierDir?: string`. `generateTokenIndex` now writes `token-index/meta.json` with `{ tierDir }` (omitted, not `null`, when not provided — `JSON.stringify` drops an `undefined` value).
- New `application-mcp-server/src/indexer/resolveThemeTierRoot.ts`: precedence `meta.json`'s `tierDir` → the caller's explicit tier (`DesignSystemRoot.tierDir`) → the legacy `<projectRoot>/src/tokens` default. Falls through silently (never throws) on a missing/malformed `meta.json`.
- `application-mcp-server/src/indexer/ModeClassifier.ts`: `load(projectRoot, tokenIndexDir?, explicitTierDir?)` now resolves the theme root via `resolveThemeTierRoot` instead of hardcoding `path.join(projectRoot, 'src/tokens/themes/dark/SemanticOverrides.ts')`. `projectRoot` is now purely the third-precedence legacy fallback.
- `application-mcp-server/src/indexer/TokenIndexer.ts`: `indexTokens(tokenIndexDir, projectRoot?, explicitTierDir?)` — same resolution; `loadThemeOverrides` now takes the resolved TIER ROOT directly (drops the `'src/tokens'` join it used to do internally).
- `application-mcp-server/src/indexer/ComponentIndexer.ts`: `IndexComponentsOptions` gained `tierDir?: string`, stored as `this.explicitTierDir`; threaded into `modeClassifier.load(...)`, the full-index `tokenIndexer.indexTokens(...)` call, and `reindexTokens` (which re-reads `meta.json` fresh on every call — no stale caching).
- Backward compatible by construction: when neither `meta.json` nor an explicit tier is available, the resolved value is byte-identical to the old hardcoded path, so every pre-existing direct caller of `ModeClassifier.load`/`TokenIndexer.indexTokens` (none of which pass the new params) is unaffected.

### `generate`'s write side anchored + the partial-state refusals

- New `src/cli/shared/errorCatalog.ts`: one function per design.md catalog row (`partialConfigNoTierMessage`, `partialUnusedLocalTierMessage`, `partialTierNoConfigMessage`, `partialManifestOnlyMessage`, dispatched by `partialCaseMessage`; plus `packageModeIndexAbsentMessage`, `bornIndexAbsentMessage`, `explicitTokenIndexMissingMessage`). Single source so `generate`'s refusal and the two MCP servers' unavailable-index logging (Task 1.6) can never drift.
- `src/cli/shared/bornRepo.ts`: `DesignSystemRoot` gained `attemptedTokenSource?: string` — the resolved (literal) `tokenSource` path for the `config-no-tier` partial case, needed to fill the catalog string's `<tokenSource>` slot. `undefined` for the non-literal case (Peter's ruling — we never read the real value).
- `src/cli/designerpunk.ts` `runGenerate`: computes `dsRoot = findDesignSystemRoot(process.cwd())` first. If `partial`, prints the exact catalog string for the matching sub-case and refuses (`process.exit(1)`) before `loadConfig` or any file write. Otherwise anchors BOTH the read side (`loadConfig(dsRoot.root ?? process.cwd())`) and the write side (`generateTokenIndex(path.resolve(generateRoot, 'token-index'), { …, tierDir: config.tokenSourceRoot })`) at the discovered root, not a bare `process.cwd()`.
- `scripts/generate-platform-tokens.ts`: added the same `tierDir: config.tokenSourceRoot` to its own `generateTokenIndex` call (a second real caller of the now-required-in-practice field).

### `figma-*` anchored (C2 consumer #5)

- `src/cli/figma-push.ts` and `src/cli/figma-extract.ts`: the three `path.resolve('designerpunk.config.ts')` sites (a bare-cwd read with no ascent) are replaced by `path.join(resolveConfigDir(), 'designerpunk.config.ts')`, where `resolveConfigDir()` calls `findDesignSystemRoot(process.cwd()).root ?? process.cwd()`. A script run from a subdirectory of a born repo now finds the real config instead of silently falling back to `dist/`.

### The two MCP servers' bootstraps (product server wiring is explicitly mine per this Task's assignment)

- `application-mcp-server/src/index.ts`: the `require.main` bootstrap now also requires `dist/cli/shared/errorCatalog`; the token-index-unavailable branch calls the new, EXTRACTED, pure `resolveTokenIndexUnavailableMessage(reason, dsRoot, packageRoot, errorCatalog, explicitEnvValue)` (unit-testable outside the bootstrap guard) instead of a generic reason-code log line. `start()`'s stale `Token index not available (Spec 096 pending)` line is removed (the specific catalog message already fires earlier, in the bootstrap block, before this server is even constructed — a second, wrong-spec-number line would just contradict the accurate one).
- `product-mcp-server/src/index.ts`: the bootstrap is rewired from the deprecated `resolveConsumerOwnedRoot` (cwd-existence-only) to `findDesignSystemRoot` + `resolveProductRoot` + `resolveComponentRoots` + `resolveTokenIndexRoot` + the same extracted `resolveTokenIndexUnavailableMessage` pattern (a second copy — sub-packages cannot statically import each other's `index.ts`, same `rootDir` boundary the CONSUMPTION CONTRACT works around for the root-level shared modules). `ProductIndexer`'s constructor still takes a single `componentDir: string` (not upgraded to multi-root in this spec — that upgrade landed only for the application server's `ComponentIndexer`, Task 1.4); the product bootstrap takes `resolveComponentRoots(...).roots[0]` (the precedence winner: consumer when born, else the package root) rather than the union.

## Application-time adaptations

1. **`generate` refuses for ALL FOUR partial sub-cases, not just the two design.md's C2 prose names by name** (`tier-no-config`, `unused-local-tier`). The bullet reads: *"`generate` refuses in `tier-no-config` (D-B2), in `unused-local-tier` (D2-B1), and in a subdirectory of a partial repo."* I read "a subdirectory of a partial repo" as covering the general remaining case — and since ALL FOUR "partial: X" rows in the design's own catalog table are refusal-shaped (three explicitly say "Refusing"; the fourth, `manifest-only`, structurally matches the same family and points at the same remediation), I judged refusing for all four — using each row's own existing catalog string verbatim — to be the more consistent and safer reading than selectively refusing for two and letting `config-no-tier`/`manifest-only` fall through to a generic downstream error. **Flagged for explicit confirmation**: this is an interpretation of an ambiguous bullet, not a literal instruction; if the intended scope was narrower (only the two named sub-cases refuse via this mechanism, with `config-no-tier` continuing to fail naturally via `resolveTokens`'s existing "Token source not found" error and `manifest-only` falling through to package-mode-style generation), that's a one-line change to narrow the `if` condition in `runGenerate`.
2. **`runProductOnly` is UNTOUCHED** — no root-anchoring, no refusal. The design bullet names `generate` generically; `runProductOnly` is a distinct, narrower CLI path that already requires `token-index/` to exist (a stronger implicit precondition than the main pipeline), and touching it wasn't asked for. Flagged as a residual, not silently dropped.
3. **`tokenOrigin` labelling is NOT added to individual MCP tool responses** (e.g. `get_token_details`, `search_tokens`). Design.md's two mentions of "labelled `tokenOrigin`" sit in the DATA-ROOT RESOLUTION section (C2/C3), describing the boot-log labelling already implemented (Task 1.2/1.4) — not the "Error Handling" catalog table Task 1.6's criterion actually names ("Every catalog string this parent emits is string-equal to its design row"), which has no `tokenOrigin` field. Adding a new field to every token-query response would be a materially larger, unrequested feature. Flagged per the orchestrator's explicit ask to resolve this conservatively rather than expand scope.
4. **Product server's `errorCatalogWiring.test.ts` was not separately bit-tested.** Its `resolveTokenIndexUnavailableMessage` is a byte-identical copy of the already-bit-tested application-server version (necessarily duplicated — sub-packages can't statically import each other's `index.ts`). I judged re-running the same revert/red/restore cycle on an identical algorithm as low-value given the time cost, and am disclosing the omission rather than silently implying it was done. If the orchestrator wants the bite repeated for the product-server copy specifically (to catch a future divergence between the two copies), it's a five-minute addition.
5. **The `build:mcp-shared` gap Lina flagged (Task 1.4 handoff) is unchanged and now also covers `errorCatalog.ts`.** `build:mcp-shared`'s esbuild command only compiles `resolvePackageRoot.ts` and `mcpDataRoots.ts`; `bornRepo.js` and now `errorCatalog.js` come only from a full root `tsc` build. `package.json` is Task 3's Primary Artifact, so I did not edit it — noted here again for the Task 3 brief (both `bornRepo.ts` and `errorCatalog.ts` need adding to that esbuild file list).
