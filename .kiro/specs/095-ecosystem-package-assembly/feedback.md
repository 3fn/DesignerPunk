### The Consumption Gap — Agree with Data, iOS Has the Same Problem

Data's R1 nails the fundamental issue: **there's no native platform consumption path.** iOS projects use SPM or CocoaPods, not npm. Running `npm install @designerpunk/core` puts Swift files inside `node_modules/`, which Xcode doesn't know about.

Data asked whether iOS has a cleaner path via SPM. The answer is: **yes, potentially, but not without work.**

SPM can reference local packages via `path:` dependencies. This means the sync mechanism for iOS could produce a local Swift Package rather than just copying files:

```
WrKingClass/
  DesignerPunk/           ← generated by sync:ios
    Package.swift         ← generated, references the files below
    Sources/
      DesignTokens.swift  ← from dist/DesignTokens.ios.swift
      ComponentTokens.swift
      ThemeAwareBlendUtilities.swift
      MotionTokens.swift
      Components/         ← from src/components/core/*/platforms/ios/
        Avatar.swift
        ButtonCTA.swift
        ...
```

The product's `Package.swift` or Xcode project adds a local dependency:
```swift
.package(path: "./DesignerPunk")
```

This is cleaner than Gradle's file-copy approach because:
- SPM handles compilation, linking, and module visibility
- Xcode recognizes the dependency and provides autocomplete
- Updates are a re-run of `sync:ios`, not a manual file copy

**However** — this requires the sync tool to generate a `Package.swift` with the correct target structure, platform requirements (iOS 17.0+), and dependency declarations (SwiftUI). That's more than a directory copy. It's a small code generator.

**My recommendation**: Align with Data. Acknowledge the gap now, document the target model, defer the implementation to M0b. The sync mechanisms will differ per platform — `sync:ios` produces a local Swift Package, `sync:android` copies files into the Gradle source tree. Same CLI interface, different output structure.

### One iOS-Specific Concern: Module Visibility

When the Swift files ship inside an npm package and eventually get synced into an iOS project, the `public` access modifiers on the component structs and token properties matter. Currently, the generated `DesignTokens.ios.swift` uses `public static let` for all tokens, and component implementations use `public struct` for views. This is correct — they need to be accessible from the consuming app's module.

But the supporting files (like `VisualStateStyles.swift`, `TokenMapping.swift`, `RoundedPointyTopHexagon.swift`) use a mix of `public` and internal access. If these end up in a separate Swift Package module, internal declarations won't be visible to the consuming app. This isn't a problem if everything lands in the same module, but it's a packaging decision that affects the `Package.swift` structure.

**For M0a**: Not a concern — iOS files are reference material only.
**For M0b**: The sync tool needs to either (a) put everything in one target (simple, all access levels work) or (b) carefully separate public API from internal implementation (cleaner, but requires auditing access modifiers). Option (a) is the right starting point.

### Integration Guide: iOS Section Needed

The Integration Guide should include an iOS-specific section covering:

### Q1: Source vs Compiled — Ship TypeScript Source for the Pipeline

**The pipeline needs TypeScript source at runtime.** Token definitions (`src/tokens/*.ts`) are typed objects that generators import directly. Theme overrides are TypeScript files. The registries, resolvers, and validators are all TypeScript. When a product repo runs `npx designerpunk generate`, the entire pipeline execution chain is TypeScript — from config loading through token resolution to platform output generation.

**What ships as TypeScript source** (executed via `tsx` at runtime):
- `src/tokens/` — token definitions (the data layer)
- `src/generators/` — platform output generators
- `src/resolvers/` — semantic override resolution
- `src/registries/` — token and component registries
- `src/validators/` — semantic validation (called before generation)
- `src/themes/` — ThemeRegistry
- `src/types/` — PrimitiveToken, SemanticToken, etc.
- `src/providers/` — WebFormatGenerator, iOSFormatGenerator, AndroidFormatGenerator
- `src/naming/` — PlatformNamingRules (token name conversion)
- `src/blend/` — BlendCalculator, ColorSpaceUtils (blend utility generation)
- `src/build/tokens/` — defineComponentTokens (component token registration)
- `src/config/` — defineConfig, ConfigLoader

**What ships as compiled JS** (for direct import by product code):
- `dist/cli/designerpunk.js` — CLI entry point (`bin` field)
- `dist/config/` — `defineConfig` with `.d.ts` type declarations (for `import { defineConfig } from '@designerpunk/core/config'`)
- `dist/browser/designerpunk.esm.js` — ESM bundle (web components)
- `dist/blend/` — compiled blend utilities
- `dist/DesignTokens.*.css/swift/kt` — generated platform tokens
- `dist/ComponentTokens.*.css/swift/kt` — generated component tokens
- `dist/DesignTokens.dtcg.json` — DTCG format
- `dist/DesignTokens.figma.json` — Figma format

### `tsx` Scope Clarification

`tsx` isn't just for loading `designerpunk.config.ts` — it's for the entire pipeline execution chain. When `npx designerpunk generate` runs, `tsx` executes the CLI, which imports the config loader, which imports the generators, which import the token sources — all TypeScript. This is fine (we've decided on `tsx` as a dependency), but the design outline should be explicit that `tsx` is a runtime dependency for the pipeline, not just a config loader.

**Sparky [@ADA]: Does `dist/config/` exist?**

**Data [@ADA]: Should the generator produce product-specific Kotlin package namespaces?**

Not for M0a. The current generator produces `package com.designerpunk.tokens`. #### [THURGOOD R1]

**Q4: `files` field (allowlist approach).**

The `files` field in `package.json` is an explicit allowlist — only listed files and directories are included in the package. `.npmignore` is a blocklist — everything ships except what's listed.

For a package that contains an entire ecosystem (pipeline source, agent prompts, steering docs, MCP servers, platform files), the blocklist approach is dangerous. Every new directory or file type added to the repo is automatically included unless someone remembers to update `.npmignore`. With the allowlist, new additions are excluded by default — you have to consciously add them to `files`.

Given that we explicitly exclude spec history, completion docs, issues, and roadmap — and those directories will continue to grow — the allowlist is the safer default. One missed `.npmignore` entry and we're shipping internal development artifacts to every consumer.

Recommendation: `files` field. The list will be long (we're shipping a lot), but it's explicit and auditable.

### The Critical Gap: Native Platform Consumption Model

The design outline lists Android files as "Internal (copied by product)" and iOS files the same way. This is accurate but incomplete — it doesn't specify *how* they're copied, and the answer matters for both M0a and M0b.

**The fundamental problem**: Android projects use Gradle, not npm. iOS projects use SPM or CocoaPods, not npm. Running `npm install @designerpunk/core` puts Kotlin and Swift files inside `node_modules/`, which neither Gradle nor Xcode knows about. There's no `implementation("@designerpunk/core")` in Maven Central. There's no Swift Package pointing at an npm registry.

**Web has a clean consumption path**: `import '@designerpunk/core/components'` → bundler resolves from `node_modules` → done. One line, zero manual steps.

**Android and iOS have no consumption path today.** A developer would need to:
1. Run `npm install @designerpunk/core` (requires Node.js in their environment)
2. Manually locate the Kotlin/Swift files inside `node_modules/`
3. Copy them into their native project's source tree
4. Keep them in sync when the package updates

That's fragile, manual, and drift-prone. It's also a terrible first experience for a native developer who may not have Node.js installed at all.

### Why This Matters for M0a (Not Just M0b)

Even though M0a is web-only, the decisions we make now about package structure affect how hard M0b is:

1. **File organization in the package determines the sync mechanism.** If Android files are scattered across `src/components/core/*/platforms/android/`, `src/blend/`, `src/tokens/platforms/android/`, and `dist/`, the sync tool needs to know all those paths. If they're consolidated under a single `android/` directory in the package output, sync is trivial. M0a is the time to get the structure right.

2. **The `designerpunk.config.ts` already has platform awareness.** Spec 094 established `name` and `abbreviation` in the config. Extending it with platform output paths is natural:

    ```typescript
    export default defineConfig({
      name: 'WrKingClass',
      abbreviation: 'WKC',
      themes: [...],
      output: './dist/tokens',
      platforms: {
        android: './app/src/main/java/com/wrking/designerpunk/',
        ios: './WrKingClass/DesignerPunk/'
      }
    });
    ```

3. **Agent prompts need to know the consumption model.** When I'm implementing an Android screen in M0b, I need to know where the token files and component implementations live in the product's Android project. If the sync mechanism doesn't exist yet, my prompt can't reference the right paths. Leonardo's agent configuration template concern (R1) applies here too — the template needs platform-specific paths.

### Recommendation: Design the Sync Mechanism Now, Build It for M0b

I'm not suggesting we build `npx designerpunk sync:android` as part of this spec — that's scope creep. But the design outline should:

1. **Acknowledge the gap explicitly.** Replace "Internal (copied by product)" with a note that native platform consumption requires a sync mechanism that doesn't exist yet.

2. **Document the target consumption model.** Something like:
   - `npx designerpunk sync:android` — copies all Android files (generated tokens, component implementations, blend utilities, motion tokens) to the configured Android project directory
   - `npx designerpunk sync:ios` — same for iOS
   - Runs automatically as part of `npx designerpunk generate` when platform output paths are configured
   - Handles the Spec 094 theme-aware output (the new `{Name}Theme` data class, `{Name}Themes` instances, `CompositionLocal`)

3. **Structure the package to make sync easy.** If the `files` field organizes Android artifacts under a predictable structure, the sync tool is a simple directory copy rather than a multi-path resolver. This is a packaging decision we can make now.

4. **Add a deferred item** for the sync CLI commands, tagged as M0b prerequisite.

### Gradle-Specific Concerns

- **Package namespace**: The generated Kotlin files use `package com.designerpunk.tokens` and `package com.designerpunk.components.core`. Products will need their own package namespace. - **Compose dependency versions**: The component implementations import `androidx.compose.*` APIs. The package doesn't (and shouldn't) declare Compose dependencies — those belong to the consuming Android project. - **R8/ProGuard**: If a product uses code shrinking, the synced Kotlin files need to be included in the keep rules. The Integration Guide should note this.

### Cross-Platform Alignment with Kenya

Kenya's routing is the same question for iOS (Swift files, SPM/CocoaPods concerns). The consumption gap is identical on both platforms. Whatever sync mechanism we design should be symmetric — `sync:android` and `sync:ios` using the same config pattern, same CLI interface, same update behavior. I'd expect Kenya to flag the same fundamental issue from the iOS side.
