## The blocker — dual-instance `ComponentTokenRegistry` (Ada's diagnosis, verified)

Component tokens are the ONLY consumer-`.ts` seam that relies on a **shared-singleton SIDE EFFECT** rather than a return value:
- A consumer's `<component>.tokens.ts` calls `defineComponentTokens(...)` (from `@3fn/core/build`), which **registers into the central `ComponentTokenRegistry`**.
- `loadComponentTokens` reads the canonical `ComponentTokenRegistry` (parent CJS cache) via `getAll()`.

Without the global register, `scopedTsRequire` (per-call namespaced tsx) loads the consumer's `.tokens.ts` inside **tsx's own module registry**. When that file imports `@3fn/core/build`, tsx resolves it **freshly** → a SECOND copy of `dist/build/tokens/index.js` → a SECOND `ComponentTokenRegistry` instance. The `defineComponentTokens` side effect registers into the **duplicate**; the canonical instance `loadComponentTokens` reads stays empty → **`Component tokens: 0`**, `components.yaml` empty.

**Decisive proof (one-line toggle):** faithful registerless path → 0 tokens; same path + `require('@3fn/core/build')` primed in the parent cache before the call → 33 tokens (incl. `inputradio.box.{sm,md,lg}` from the decisive transitive-relative-`.ts` file). So tsx's scoped require *delegates* to a parent-cached `.js` when present, but loads its own duplicate when not.

**NOT the feared failure:** the transitive relative raw-`.ts` resolution (`../../../tokens/SizingTokens`) and the rewritten `@3fn/core/build` (compiled dist via 3b) BOTH resolve correctly registerless — `scopedTsRequire` returns the file's exports fine. The split is purely module-identity of the shared registry singleton across the tsx boundary.

**Why 9.5.1/9.5.2/3b didn't catch it:** 9.5.1 proved `resolveTokens` (a return value); the C′ test (9.5.2) exercises `buildConsumerMap` (`yaml.load` of `.schema.yaml` — no TS require at all). Neither touches the side-effect-registration path. The global register (present until 9.5.3) made `@3fn/core/build` resolve to one instance, masking the split.

## Fix options (Ada's; for the Lina+Ada+Peter decision — do NOT force one)

1. **Consume the return value, no shared singleton (Ada's recommendation; most aligned with the target model).** `loadComponentTokens` collects tokens from the loaded modules' **exports** (the `.tokens.ts` already `export` the `defineComponentTokens(...)` result, e.g. `RadioSizingTokens`) rather than reading a cross-boundary registry singleton. Removes the shared-mutable-singleton-across-the-tsx-boundary entirely — the exact pattern that broke. **Cost:** a component-token-authoring/collection convention change (how `loadComponentTokens` harvests tokens from heterogeneous exports) — Lina's component-architecture domain.
2. **Share the parent CJS cache for compiled `@3fn/core/*` dist `.js`.** Prime/dedupe so the scoped seam delegates `@3fn/core/build` (and its registry) to the parent — one instance. **Smallest/most targeted, proven** (the priming toggle). **Cost:** relies on tsx's delegate-to-parent-cache behavior (a bit implicit); a seam (`scopedTsRequire`/`loadComponentTokens`) change.
3. **Process-global registry handle** for `defineComponentTokens`. Avoids module-singleton identity, but reintroduces process-global state (against the no-global-residue value).
