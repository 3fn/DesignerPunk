## Genuinely useful (verified)

1. **`loadComponentTokens` and `resolveTokens` are history-laden, fragile consumer-`.ts`-resolution sites — and 117 R4 is their origin.** Spec 117's audit (`117/findings/audit-report.md` F3a/R4) found the package-mode gate *skipped* `loadComponentTokens`, dropping 27 component tokens. 117 R4 fixed it by making `loadComponentTokens` **discover + `require()` component `.ts` from the consumer's source at runtime** — which *relies on a runtime TS loader* (the bin's global tsx register). **This is exactly why Ada's bundle attempt re-broke it this session** (the `__dirname` shift made it scan `dist/*.js`, zeroing component tokens). → The audit's site inventory (a) should START with `loadConfig` (already scoped, Inc-1), `resolveTokens`, `loadComponentTokens` as the *known* consumer-`.ts` sites, but must VERIFY completeness (check `generateProductTokens`, `validateProductTokens`, and any other `require()`/`import()` of consumer paths).

2. **There are multiple generation entry points, each resolving TS differently.** Documented CLI (`npx designerpunk generate` → bin/tsx-register → CLI); the build script (`generate:platform-tokens` → tsx + the injected `(p)=>import(p)` seam); and Spec 117's now-**retired** `runGenerate`-via-ts-node-workaround. The audit's (a) must inventory the *current* set and how each resolves consumer + package `.ts` — the bin is not the only path.

3. **The bundled-subsystem exemption principle has a HARD LIMIT at the CLI (challenge of `118/findings/mcp-browser-exemption-boundary.md`).** The doc's principle — "bundling resolves imports at build time → no runtime resolution → exempt" — is TRUE for the 3 MCP servers + browser bundle, which are fully self-contained after esbuild. **It does NOT extend to the CLI:** the CLI has an *irreducible* runtime-TS need — it loads the **consumer's** `.ts` (token source, components, config), which lives in the consumer's repo and cannot be resolved at our build time. So the audit's target model (d) **cannot conclude "just bundle + exempt the CLI"** (the literal 2026-06-10 issue fix). The coherent shape is a *hybrid*: the CLI's own code may be compiled/bundled, but a **scoped** runtime TS loader (the Inc-1 `loadConfig`/Approach-A pattern) must remain for consumer `.ts`. The exemption doc itself notes (line 100) the MCP servers are exempt *precisely because* they "do not load consumer configs" — the CLI is the opposite case.

4. **Changing the consumer-`.ts`-at-runtime model re-touches 117 R4's contract.** 117 R4 deliberately made component-token loading a *source-presence discovery* over the consumer's `.ts`. If the audit's target model leans "precompile at `init`" instead of "scoped-tsx-load," it is changing 117 R4's contract — note the coupling so it's a deliberate decision, not an accidental regression.
