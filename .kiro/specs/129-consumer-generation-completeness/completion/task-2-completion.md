## Application-time adaptations

1. **The parsers are not imported statically.** The plan at integration was to replace `compare.ts`'s untyped `loadParser` with static imports. A trial showed a load-time cycle: both parsers import values from `compare.ts`, and `parse-kotlin.ts` reads `KOTLIN_COMPILE_TASKS` at load, so with `compare.ts` loaded first the suite fails to run with `TypeError: Cannot convert undefined or null to object` (at `parse-kotlin.ts` L73). Breaking the cycle with a third module would edit Kenya's and Data's import lines, which are their files. So `compare.ts` now has `loadSwiftParser` and `loadKotlinParser`: a `require` at the time a run file is read, annotated `typeof import('./parse-…')` and assigned to `ParseSwift` / `ParseKotlin`. tsc checks each parser's export against the 2.1 interface. Falsified: a scratch copy of `parse-kotlin.ts` with an extra parameter gives `TS2322: Type '(input: KotlinParseInput, extra: number) => KotlinParseResult' is not assignable to type 'ParseKotlin'` at the loader's assignment.
2. **Data's dissent on location-less `e:` lines** (he prefers `unrooted`; `task-2-3-completion.md` adaptation 10) is recorded there, and the parser builds to the README rule as ruled at `3a9f02500`. The orchestrator routes it to Stacy's review of the failure cases. This parent does not reopen it.
