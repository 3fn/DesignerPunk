## 1. What changed

- **The four primitives in OKLCH** (`src/tokens/color/primitives/shadow.ts`, new; exported from `src/tokens/color/index.ts`): `shadowBlack100` l 0 c 0; `shadowBlue100` 0.2161 / 0.0306 / 269.6; `shadowOrange100` 0.1956 / 0.0127 / 67.0; `shadowGray100` 0.1912 / 0.0219 / 263.8 — design § 8's values, no new name, no colour change (the sRGB hex of each is the hex of its earlier `rgba`). They join `composedColorMap` and a new `allEmittedColors` (the composed palette plus the four), which the three platform emitters now iterate. `allComposedColors` stays the 50-colour palette, so its tests are unchanged. The shadow colours carry no `channels` (the channel structure is Spec 133's, design § 8); `ComposedColor` is unchanged and a `ShadowColor` type is `Omit<ComposedColor, 'channels'>`.
- **Web**: `WebFormatGenerator.formatCompositeShadowToken` builds the colour from the token's colour primitive, `color-mix(in oklab, var(--shadow-blue-100) calc(var(--shadow-fab-opacity) * 100%), transparent)`, instead of the literal `rgba(0, 0, 0, …)`. The three blue-tinted composites now read `--shadow-blue-100`.
- **Native**: every shadow composite is a generated `ShadowToken`, not `Typography(…)`. iOS emits `public struct ShadowToken: Sendable` (offsetX, offsetY, blur, opacity as `CGFloat`; `color: Color`) before `DesignTokens`; Android emits `data class ShadowToken(offsetX, offsetY, blur, opacity: Float; color)`. The 24 typography composites still use `Typography(…)`: the type table is U4.
- **The warning**: `KNOWN_UNEMITTED_SHADOW_COLORS`, the `knownDefect` field, `knownShadowColorWarning` and `generate`'s warning are removed (`src/validators/ColorReferenceEmissionValidator.ts`, `src/generators/generateTokenFiles.ts`).

## 3. Application-time adaptations

- **The composite's colour is mixed with `color-mix(in oklab, … , transparent)`**, not CSS relative colour syntax (`oklch(from var(--c) l c h / var(--o))`). Both give the same computed colour; `color-mix` is supported earlier (Safari 16.2 against 16.4+, Firefox 113 against 128). The composite names the colour primitive's own property (`--shadow-blue-100`), not the composite's `-color` property, so "the composite uses its colour token's custom property" holds on a plain reading; the `-color` property is still emitted.
- **The Android `ShadowToken.color` is written `androidx.compose.ui.graphics.Color`**, not `Color`: `package-drift-validation.test.ts` reads any `val <name>: Color` in the file as a member of the theme data class, and the short form made it flag every component's `theme.` read. The full name also needs no import. The type table (U4) may change it.
- **`src/tools/integrity/Invariants.ts` and its test are outside Task 8's Primary Artifacts** (an `unlisted` instrument, found by a red suite). Its P3 invariant was a tripwire for exactly this change ("the shadow OKLCH migration may have landed; revisit the SHADOW_COLOR_PRIMITIVES allowlist"). I emptied the allowlist and flipped the two tests that pinned the shadow family as the rgba carriers. Recorded under `## Found later` in `task-8-instruments.md`; its owner is not named in the file.
- **`token-index/primitives.yaml` is a derived artefact outside the Primary Artifacts**, regenerated and committed because `tokenIndexPlatformNames` and `Invariants` read it.
- **DTCG/Figma consumers see hex for the four shadow primitives**, as for every other primitive; the semantic shadow composites already merged to `rgba` and are unchanged. Not asked for in the design.
