## 1. What changed

- **`harness/ios/lane.ts`** (new): one script that runs either iOS context. It builds each `swiftc` invocation from `harness/pins.yaml` § `ios`; compiles Stage T (the generated files, module `DPHarnessTokens`, Swift 6, `-emit-module`), Stage P (the probe, module `DPHarnessProbe`, plain `import`, `-I` Stage T's folder), Stage C (package files then generated files, module `DesignerPunk`, Swift 5) and the T5 baseline (the generated files alone, Stage C's flags); prints each invocation and its file list in the order the compiler got them; computes the floor per tier from the tarball's file list and the generated list, and prints it beside the count given to the compiler; writes `run.json` and `logs/*.txt` in the format `harness/README.md` § "The comparator's command line" specifies. It decides no verdict.
- **`scripts/harness/probe-swift.ts`** (new): the probe generator. It reads `token-index/{primitives,semantics,components}.yaml` and the consumer's registered themes and emits `Probe.swift`: one `_ = DesignTokens.<name>` per primitive and semantic iOS name, `_ = <name>` per component name, one read per list element, one `_ = <Name>Themes.<instance>.<member>` per `theme.`-named colour per registered theme instance, and one `_ = EnvironmentValues().dpTheme`. `n` (counted from the emitted text) and `m` (counted from the index and config by a separate function) are compared; Stage P prints `probe: read <n> of <m> index names (…)`.
- **`harness/ios/selftest/**`** (new): `missing-return.swift`; `planted/PlantedTokens.swift` and `planted/token-index/*.yaml` (two names, one `internal` member). Their use is 3.3's.
- **`harness/ios/README.md`** (new, inside the grant `harness/ios/**`): how Task 5's workflow calls the lane, what it writes, its exit codes, and `--read-toolchain`.
- **`scripts/harness/__tests__/probe-swift.test.ts`** and **`scripts/harness/__tests__/fixtures/swift/index-themes/**`** (new): the probe tests, and tests of the lane's pure helpers and of both contexts end to end against a fake `swiftc`.

## 3. Application-time adaptations

1. **3.2 and 3.3 landed in one commit.** The stages and the self-tests are one script, and the stage runner is what the self-tests call. Splitting the file by subtask would have meant writing a version of `lane.ts` that never existed. Each subtask still has its own doc; 3.3's covers the self-tests and the toolchain match.
2. **The lane is TypeScript run by `tsx`, not a shell script.** The file ordering, the floor, the toolchain parse, the pin read and the run-file JSON are all easier to get right and to test in TypeScript, and it can import the committed parser, the probe generator and the comparator's `RunFile` type. Its tests live in `scripts/harness/__tests__/probe-swift.test.ts` rather than beside it: `scripts/jest.config.js` has `rootDir: scripts/`, so a test under `harness/ios/` would not be selected by `lane-functional-root`. That puts lane tests in a file named for the probe.
3. **The instance names the probe reads a theme colour through are my derivation, because the spec states them only by example.** Req 4.1 says "base light and dark, WCAG light and dark"; design § 4 lists `baseLight, baseDark, wcagLight, wcagDark …` and "one member per registered theme and mode". `init`'s scaffolded config registers a theme `dark` in mode dark and a theme `wcag` in mode light. My rule (`themeInstances` in `probe-swift.ts`): `baseLight`, `baseDark`, then for each registered theme `<t>Light` for mode light or both and `<t>Dark` for mode dark or both. That gives `baseLight, baseDark, darkDark, wcagLight`, not the design's four. **This contradicts the design's example and is Ada's to settle in Task 11 (U6).** I chose to read an instance the emitter may not declare, because a compile error is loud and a silently skipped instance would hide the gap D1 exists to catch. The rule is one function; Task 11 changes it there.
4. **The consumer's themes come from `harness-consumer.json`, not from loading the consumer's config.** *(Changed after the first commit, 2026-11-06, on the coordinator's direction.)* My first version ran the installed package's config loader with `NODE_PATH` at the repository's `node_modules`, because `consumer.ts` prunes the consumer's `node_modules` and the manifest then carried no themes. Ada's `38d1d8ac0` added `themes: [{name, mode}]` (config order; an absent key reads as none) to the manifest, and the unit head is now that commit. I merged it (`1550d7093`), removed `loadProbeConfig` and every `NODE_PATH` read from `harness/ios/lane.ts`, and added `probeConfigFromManifest`, which reads `name` and `themes` from the manifest. The lane now reads the consumer as an adopter's install would. Tests: the manifest read, an absent key, a malformed theme, the probe's reads over the manifest's themes, and that no `node` process runs and `lane.ts` holds no `NODE_PATH`. A real run on a fresh `consumer.ts` output gave the same `read 481 of 481` as before.
5. **The `\.dpTheme` read counts toward `m`.** The criterion says "one read through `\.dpTheme`" and "read count equals the index's iOS names". The key read is not an index name, so I count it in both `n` and `m` and show it in the breakdown (`key 1`), and I make it only when the index names at least one `theme.` colour. So the planted fixture reads `2 of 2`.
6. **The probe is generated, and its count checked, even while Stage P is blocked.** The criterion says only that a blocked Stage P prints `probe: blocked (token module not built)`, which it does. The generator's `n = m` does not need the compiler, so a generator that drops a name fails the context even while Stage T is red. The lane prints a second line `the probe was generated but not compiled: probe: read n of m …` beside it.
7. **A generated file wins a name clash; the package's `dist/DesignTokens.ios.swift` is dropped.** "One copy of each native file name" does not say which copy. The consumer's own generated output is the input under test, and the package's `dist/DesignTokens.ios.swift` ships in the tarball, so the generated one is kept. Among packaged files the first by path is kept. Each dropped file is printed with its reason.
8. **The iOS probe reads no product-token member.** Task 3's criteria name none; Task 4's Android criterion does ("one read per product-token fixture member"). The product-token file is compiled by Stage T either way. A cross-platform asymmetry for Leonardo to rule on, not something I filled.
9. **Observation from the local run, not a finding of record.** Index names such as `AvatarTokens.sizeXs` (23 component names by a rough text check) do not appear in the consumer's generated `ComponentTokens.ios.swift`; Stage P will read them as `cannot find 'AvatarTokens' in scope` once Stage T builds. That is item (ii) (the component tier reaching `generate`, Task 13), and the first baselines will show it.
