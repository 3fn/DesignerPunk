## 2. Item 1 — human review binds system tokens

**The definition has one home, Token Governance (site 2); Core Goals points to it (site 1).** This is Thurgood's R1 item 1, on the principle Peter ruled for the selection order (6(ii), pointer only). A **system token** is a Rosetta token: a primitive or semantic token in the token source, or a component token declared with `defineComponentTokens()` (a component's `*.tokens.ts`). The token source is `src/tokens/` in DesignerPunk's repo. In a product it is the directory `tokenSource` names in `designerpunk.config.ts` (`src/config/defineConfig.ts` L49–55); `init` writes `./src/tokens` (`src/cli/init.ts` L761), but the path is configurable. In package mode, with no `tokenSource`, the product's primitives and semantics come from the installed package, so they can be added only upstream; its component tokens are still system tokens (`componentTokens`, `defineConfig.ts` L44–45). A **product token** is one in `product/tokens/*.yaml`, governed by Product-Token-Governance. Product-Token-Governance L40 already says the same of component tokens: "they are system-level tokens with component-scoped consumption, governed by Ada + Lina".

*(Correction to the brief's shape, which put component tokens "in `src/tokens/`": they are declared in `src/components/**/*.tokens.ts`, and a product points `componentTokens` at its own directories. `src/tokens/component/progress.ts` is the one component-token file under `src/tokens/`. The definition names the declaration, not the directory, so it is right in both repos. Lina R1 item 4 confirms it for her domain, including its consequence: a product's own component declares its tokens with `defineComponentTokens()`, so they are system tokens and need human review.)*

>
> **Leonardo** defines product tokens during screen specification. He identifies product-level values, names them, and documents their purpose. This is the primary authoring path.
>
> **A need the spec missed.** A platform agent (Sparky, Kenya, Data) that sees a missing need while reading the spec raises it before building (Product-Handoff-Protocol § "Platform → Leo (Raising Concerns Before Implementation)"). Some needs appear only during the build on one platform, such as spacing added to a safe-area or keyboard inset (the inset itself is the platform's value, not a token) or a sheet detent height. A platform agent that meets one first checks the system tokens, semantic first; a need they cover is not a gap. Otherwise it surfaces the need to Leonardo as a Tier 1 clarification (Product-Handoff-Protocol § "Tier 1: Quick Clarifications"), stating the need, the system tokens it checked, and a proposed name with its `ref:` or `value:` and rationale. ⟦F-B2⟧ ⟦F-A⟧ The outcome is recorded in the Implementation Report under "Decisions Made During Implementation", and the screen spec is amended to name any token that is kept.
