# Ballot Measures — Conventions & Ratification Protocol

**Date**: 2026-07-05
**Purpose**: How ballot measures are drafted, reviewed, ratified, and applied — including the record-first ratification protocol (Peter-approved 2026-07-05)
**Status**: Point-of-use convention. The durable law home for this protocol is a 125-formalization decision (classification map) with 122 propagating the agent-facing rule; see the inbound notes in both specs.

---

## Lifecycle

1. **Draft** — an agent (typically Thurgood for Civitas surfaces) authors the measure: problem evidence, proposed before→after edits for every affected site, scope decisions, reviewer list. Status: `DRAFT`.
2. **Review** — named reviewers respond per the Spec-Feedback-Protocol stamp format; the author incorporates (woven, not appended) and records the round in the ballot.
3. **Ratify** — Peter approves, modifies, or rejects.
4. **Apply** — the edits land exactly as written; verification per the measure's own mechanics (metadata validation, MCP index rebuild, straggler sweep).

## The Ratification Protocol (record-first) — approved by Peter, 2026-07-05

**Authority is a committed record, not a message.** The protocol:

1. When Peter ratifies, the session that received his ratification **first** updates the ballot's `Status` to `RATIFIED (Peter, <date>)` and **commits that record** — before any law edit is applied. The commit's author and timestamp make the ratification auditable.
2. Any agent asked to apply a ratified measure verifies **one mechanical fact**: the committed ballot says `RATIFIED`. If it does, apply; the applying agent makes **no authority judgment** about who relayed the instruction or how.
3. If the committed ballot does NOT say `RATIFIED`, do not apply — and do not refuse-and-stop either: report the missing record so the ratifying session can commit it. The failure mode to avoid is symmetric: rubber-stamping unverifiable claims AND refusing legitimate orchestration are both wrong; the record check replaces both judgments.

**Why (the 2026-07-05 lesson):** during this directory's first ballot, an applying agent refused a relayed ratification claim it could not verify — a refusal that added friction to a true ratification while providing no protection against a false one (the relaying session held the same write access and applied the edits itself). The gap was structural: authority existed only as a claim in a message. This protocol makes it a verifiable artifact instead — the same principle as the rest of the system's mechanical turn: *claims are suggestions; records are contracts.*

**End state (Spec 125 Phase 0+):** once the PR-gated workflow exists, ratification of governance-law changes becomes **Peter's PR approval** (branch protection + code-owner review on `governance/`) — platform-verified authority, superseding step 1's manual record for the cases the gate covers. The committed-record protocol remains for artifacts outside the gate's reach.

## Conventions

- **Location**: measures arising from specs live as spec artifacts (precedent: 118 Task 11, 117 Task 6); measures arising from governance reviews or standalone findings live here, named `YYYY-MM-DD-<slug>.md`.
- **Edit discipline**: apply "exactly as written"; if a before-text does not match, stop on that block and report — never adapt silently. Application should end with a mechanical sweep for the edit-class (a straggler grep), not trust in the enumerated list — every count in this directory's first ballot was wrong at least once (two → three → four occurrences); the sweep caught what the lists missed. **Superseded text**: a document agents read as law carries only the current text plus a dated pointer (`amended <date> by <ballot> <item>; prior text at <SHA>`); ledgers — issue records, claims-pass records, signature sheets, completion docs — keep superseded text inline, labelled and dated *(Peter, 2026-10-19; ballot 2026-10-18-sitting-2-subtask-tests-tasks-sweep-criteria-form S5, F-S5-record)*.
- **Instrument census** *(ballot 2026-10-19-instrument-census-at-draft)*. A **registered instrument** is the code a check runs, where the check is named in the `checks` of a `governance/classification-map.md` row, or of one of its `scope[]` entries, at `check_state` `proposed`, `armed` or `dormant`. An item is **presumptively in scope** when it meets any of three conditions: one of its edit sites is a file the check's command loads; one of its edit sites is a file that the row's `education` homes, or the instrument's code, cite as the law it implements; or the item names an instrument code change to follow it. Changes to messages or output format only are out of scope. Every presumptively in-scope item carries exactly one `**Census**:` line, in one of the three forms below, and a missing line is a finding on the drafter.
- **Census**: `**Census**: <command> over <corpus> @ <sha> — current <digest> → proposed <digest>; <N> <unit> change (delta: § Census appendix)`. The census runs the instrument's **census mode**, which is the command on its row's `census` field. That command calls the instrument's own decision code once per input and adds no logic of its own. It runs at one `main` SHA: once as committed, and once with a scratch diff that applies with `git apply` at `<sha>` and touches only the instrument's code. Its output is one sorted line per input, `<input>\t<verdict or surface digest>`, followed by the selected count. `<digest>` is the sha256 of that output, and the delta is the inputs whose lines differ. `<corpus>` names the surface the amended code reads, and `<unit>` is the instrument's input grain (a file, a contract, a matched substring). The scratch diff and the delta go verbatim in a `## Census appendix` at the ballot's end. A hand count may accompany the census, labelled heuristic. It never substitutes, and where the two differ the item reports both and rests on the instrument's.
- **Exempt**: `**Census**: exempt — <ground>; ran: <the input actually run, or none>; count: <a hand count labelled heuristic, or no count>`. There are three grounds. (1) The instrument does not exist at `<sha>`. (2) Its row reads `census: none — <why>`, written by the owner. (3) The rule's effect lies only in tools that no single registered check's command composes.
- **Not in scope**: `**Census**: not in scope — <instrument> — <why no verdict or surface can change>`.
- **The census reader** is Stacy, and where she drafts the item, Thurgood. At the ballot's review the reader reads every presumptively in-scope item's line, whether or not she is the ballot's required reviewer. The read covers the line's presence and grammar, the in-scope call, and the exemption ground. It also reproduces both digests at `<sha>`, current and proposed, and the delta. A failure on any of them voids the census. A disputed exemption or not-in-scope line goes to Peter.
- **Re-runs**: at application the census is re-run and compared input by input with the ratified delta. A difference in an input unchanged since the census SHA (`git diff --name-only <census-sha> <run-sha> -- <corpus>`) stops that item, which is reported, not adapted. Differences in inputs that changed since then are listed. An exempt item's application run is compared with its count, and a difference stops it in the same way. The PR that ships the instrument change runs the scratch diff and the shipped code at its own base. Their digests must be equal, with no carve-out, or the PR stops and reports.

## When a governance edit needs a ballot — three kinds

*(Ballot 2026-10-18-governance-edit-kinds.)* Every edit to a **governance path** — `governance/**`, `.kiro/steering/**`, `.kiro/hooks/RELEASE-FLOW.md`, and the prose of `canonical/agents/**` — is exactly one kind, named in the PR body (Task-Completion-Protocol § "Branch and PR Conventions"). **The kinds decide whether a ballot is needed, never who merges**: every PR on these paths stays Peter-merged under the carve-out. "Governance text" includes every one of these paths, and an edit to a seat's write scope or role is always LAW.

| Kind | What it is | Authority | Ratification |
|---|---|---|---|
| **LAW** | A change to what governance requires | a ballot | record-first ballot |
| **PRE-DECLARED EXECUTION** | A merged design clause or a ratified ballot names the edit before it is made | the named clause | no ballot; the PR body cites the clause; the doc's owner reviews the text |
| **CONTENT CORRECTION** | An observed falsehood **or omission** in instructional or descriptive text, with no clause naming the fix — **never a change to what governance requires** | the observation (record cited) **and a referent** that is not governance text in the same PR and not enforcement code changed in the same PR (below): the code, the ratified law or the observed behaviour the new text matches | no ballot; the owner's fix PR, carrying a `**Consulted**:` line that names **the referent's owner** when that is not the author (`none needed — author owns the referent` otherwise) |

**What passing establishes, and what it does not:**
- **LAW** establishes that Peter ruled the requirement. It does not establish that the text is applied, or right in every reader's context; application is verified by the ballot's own mechanics.
- **EXECUTION** establishes that the edit is the one the clause named, as the owner reads it. It does not establish that the clause was right, and it covers nothing beyond the named edit: excess text in the same hunk is LAW or CORRECTION and is named separately.
- **CORRECTION** establishes that the old text was false or incomplete by the cited observation, and that the new text matches the cited referent. It establishes no requirement and changes none.

**The test between CORRECTION and LAW**: a correction needs a referent that already held before the PR, or that only *describes* — never one that *requires*. Two kinds of referent changed in the same PR never count: **governance text**, and **enforcement code** — the gate-instrument paths of ballot `2026-10-17-standing-write-scope-six-roots` § 3 item 4 (its § 4 B checker list, `scripts/check-completion-criteria-parity.ts`, `scripts/completion-claims/**`, `tools/agent-generator/verify-gate-registration.sh`, the three steward-verb tool files), `.kiro/hooks/**`, `.github/**`, every check named by a required job in `EXPECTED_CONTEXTS` (`tools/agent-generator/verify-gate-registration.sh` L63), and any other check whose failure blocks a merge or a release. Code that declares behaviour (a component's `contracts.yaml`, its source) may be a same-PR referent. If a reader must now do something that nothing already required before the PR, the edit is LAW. **When in doubt, LAW.**

**The rot mode, named**: a LAW change dressed as an EXECUTION or a CORRECTION to skip the ballot. Its detector is the claims-pass read (Stacy's charter, "The governance-edit-kind read").
