> **Why major, and the counter-argument that survives.** One change removes something a 15.1.0 install relies on: **`Input-Radio-Set` now requires `accessibilityLabel`** (#352). A 15.1.0 call site is a compile error in typed TypeScript (and in Swift and Kotlin, if you build the native reference source); on web it is not a build error, but the group renders with no accessible name. Required-where-optional-before is breaking by definition, and the accessibility reason (WCAG 4.1.2: a radio group needs a name) is why it is required rather than defaulted. **Peter ratified 16.0.0 as MAJOR on 2026-10-15 (release-4 rulings item 20).**
>
> **What survives**: two changes classed 🟡 minor can also turn a 15.1.0 green into a red with no change on the consumer's side.
> - **`validate_assembly` now fails a tree with a wrong prop value** (#359). These notes hold that the tree was already wrong (the value was never one the component accepts) and the tool now says so, so it is a new check, not a removed guarantee.
> - **`find_docs` in concept mode now returns 20 matches by default with a `nextCursor`** (#360). Tooling that called it with a `concept` and expected every match in one response now gets the first page.
>
> On the strict reading "anything a 15.1.0 user must change is breaking", both qualify, and this release would list three breaking changes, not one. The bump is the same either way; what the classification changes is **where a reader finds them**. The CHANGELOG lists both under "Changed", names both in its opening paragraph, and its "Upgrading" step 3 covers `validate_assembly`. Its "Upgrading" step 7 covers `find_docs` paging. A reader who scans only "Breaking" still meets neither.

**Scope of this release, plainly**: This release is ready for building web products, with the agent layer for Claude Code and Kiro. Native onboarding is not supported yet: the iOS (SwiftUI) and Android (Jetpack Compose) components ship as reference source, not a build input, so don't start a native product on this release. On web, a custom theme you register in `designerpunk.config.ts` does not change your generated output yet; light and dark mode work.

## 🔴 Breaking

- **`Input-Radio-Set` requires `accessibilityLabel`, the radio group's accessible name** (#352). It is not drawn on screen: show the visible question as your own text and pass the same words here.
  - **Web**: the `accessibility-label` attribute on `<input-radio-set>` (or the `accessibilityLabel` property from script); it becomes the `aria-label` of the group's `role="radiogroup"`. A missing, empty or whitespace-only value is not a build error: the group has no accessible name, and a development warning in the console names the missing attribute.
  - **SwiftUI**: `accessibilityLabel:` is the second argument, after `selectedValue:`. It replaces the fixed "Radio group" label the component used to announce.
  - **Jetpack Compose**: the named parameter `accessibilityLabel` (a `String`, no default).
  - The Application MCP's `validate_assembly` warns about a tree that leaves it out, and the form experience patterns (`multi-section-form`, `view-edit-screen`) tell your agent to supply it.

## 🟡 Added and changed capability

- **`validate_assembly` checks prop values against each component's schema** (#359). A wrong value for a known prop is an error naming the prop and its allowed values (for example Button-CTA `size: "md"`, or a colour prop that is not a colour token). It also **warns** about a prop name the schema does not list and about a missing required prop (callback props exempt). Not checked: data bindings, functions, objects, `IconName` values and free-form strings. **A tree that passed on 15.1.0 can now fail.**
- **`find_components` states that filter rows are untiered** (#359). Without `keyword`, `context` and `category` are exact filters: their rows carry no `matchConfidence`, `matchedOn` or `rank`, in name order. Only the tool's description changed.
- **`find_docs` concept mode pages** (#360): 20 matches by default (`limit` up to 100), a `nextCursor` while more remain, cut after ranking so the first page holds the best matches. List mode is unchanged.
- **Consumer agents' write scope: a pre-approved set plus a human-confirmed exception** (#377). Each generated consumer agent's "Write scope" section said the agent may write only under its listed paths and must treat everything else as read-only; in Peter's six interactive Kiro runs (2026-10-16, evidence kept outside the repo) that sentence held even against an in-session grant, so consumer-Sparky refused the screen code a Leonardo spec asks for. It now says the listed paths are pre-approved and that for any other path the agent asks its human first and writes only after they confirm in that session. Per target: Kiro may also show its own permission prompt; Claude Code may not, so the human's confirmation is the check. All 16 consumer renderings carry it; the steward (DesignerPunk's own) renderings are byte-identical. Kiro's `allowedPaths` are unchanged.
- **Consumer-Leonardo can write screen specs where `find_screens` reads them** (#378). `product/**` joins his write scope, and his "Specify the Screen" step gains a "Where it goes" line: `product/experience-map/pages/`, with the Integration Guide § "Product Data Directory" for the full tree. Before, his only writable path was `specs/**`, so the screens he wrote were invisible to the Product MCP (trio-3, R3-5). **Consumer-Sparky's token line** now tells him to link the repo's own `DesignTokens.web.css` in place of DesignerPunk's base `tokens.css`, alongside the component-token stylesheet INSTALL § Web names (R2-2). Leonardo and Sparky signed both changes (signing commits `c18a02e0d`, `9e5ede426`). DesignerPunk's own Leonardo gains `product/**` too; it is inert in this repository.

Both agent changes reach a consumer's repo through `sync`, as regenerated agent files.

## 🔵 Changed

- **Button-CTA's contract no longer claims `state_loading`** (#369). `contracts.yaml` (now 2.0.0) listed it as required on web, iOS and Android; none of the three implementations has a loading state. The Application MCP no longer lists it; Component-Family-Button and Component-Inheritance-Structures were corrected in the same PR. A loading state is planned for 16.x.
- **The install guide** (`docs/consumer/INSTALL.md`, and the Integration Guide it is generated from):
  - **The restart step says what each tool asks** (#362): Claude Code asks you to trust the folder and then to enable the three MCP servers; Kiro asks nothing. The README's "Getting Started" says the same. Source: the cold-observation table (`.kiro/specs/123-consumer-distribution/validation/cold-observation-table.md`).
  - **More of what you meet on the way in** (#375): which parts of your token source `generate` does not read yet; how to keep `init` from breaking a TypeScript host's own build; how a no-build web page loads the components (served over local HTTP); what a joining teammate commits after `attach`; and, for 14.x upgrades, that `sync`'s pre-apply report shows the pre-conversion state and the old manifest is kept.
- **The browser distribution guide** (#375) tells you to link your own `DesignTokens.web.css` in place of the base `tokens.css`, and its token list and custom-style example now name CSS custom properties that exist (six of the names did not).
- **Served governance documents**: the `Process-Cross-Reference-Standards.md` anti-pattern example no longer carries a developer's home-directory path (#367); `Token-Family-Opacity.md` carries a "Section Revised" line for § Disabled States (2026-09-18, #170) and says Button-CTA's loading state is not yet implemented (#375); `classification-map.md` gained and amended register rows for DesignerPunk's own release law (#354, #355, #370, #376). ## 🔵 Fixed

- **`init` refuses where no terminal is attached, instead of waiting forever** (#372). Without `--name` and `--abbreviation` it exits at once, names both flags and writes nothing (`--name=<name>` and `--name <name>` both work). A `.gitignore` that `init` creates now has `node_modules/` above DesignerPunk's block, as your own line that `sync` never changes; an existing `.gitignore` is left as it is. `--help` says the two flags are required off a terminal, lists `--re-scaffold` and `--yes`, drops `--skip-components` (still accepted, does nothing) and names the install guide, as `init`'s closing output now does. `init`'s born-repo refusal says what Claude Code and Kiro ask on restart.

## ⚠️ Known limitations (disclosed, tracked)

- **Part of the token source `init` copies into your repo is not read yet.** `generate` takes these from the installed package, so editing them in your copy does not change your output: the colour palette; the dark and WCAG override maps; the opacity values that colours with transparency are built from; the motion tokens (duration, easing and scale) and the layering tokens; the font-size and line-height values that icon sizes are calculated from (your own font-size and line-height tokens are still read from your copy); and the whole DTCG/Figma export. Spacing and the other non-colour primitives, and your semantic references, are read from your copy. This was already true in 15.0.0 and 15.1.0; it is stated here for the first time. The list is the one the read-site inventory test found (#368, `src/generators/__tests__/fixtures/token-read-sites.json`): it corrected the first draft, which missed the opacity, icon-size and motion-scale reads. That test fails when a file gains or loses a token import, so the list cannot silently grow; it does not check this sentence. Tracked: `.kiro/issues/2026-10-15-123-palette-read-from-package.md` (rulings item 27: palette first, target 16.1).
- **`get_token_consumers` in a repo created with `init` counts only your own components**; DesignerPunk's components are not counted (rulings item 13; fix at release 5).
- **`blend.disabledDesaturate` and `disabledColor()`/`disabledBlend()` are still deprecated, not removed.** They were deprecated on 2026-07-15 as "scheduled for removal in the next major version", and the served `Token-Family-Blend.md` and `Token-Family-Color.md` still say so. Neither 15.0.0 nor this release removed them; removing them is itself a breaking change and was not planned for 16.0.0.
- **Carried from 15.1.0, unchanged**:
  - `validate`'s mathematical-relationships check fails on unmodified token source, so `validate` exits non-zero. Tracked: `.kiro/issues/2026-06-24-mathematical-relationship-parser-validation-gaps.md`.
  - Native onboarding is not supported: no theme surface is emitted, the 14 theme-varying semantic colours are absent from the native token files, and nine shipped iOS files misspell the theme key. Tracked: Spec 129, `.kiro/issues/2026-10-03-ios-theme-environment-key-missing-backslash.md`.
  - Custom themes are not emitted on any platform.
  - The Application MCP reads 32 of 34 DesignerPunk native implementations as `scaffold`. Tracked: `.kiro/issues/2026-10-13-native-readiness-test-patterns-miss-repo-tests.md`.
  - Upgrading from 14.x: `sync` does not detect copied component-token files in the pre-fix form (R1), and `--migrate-components` reports "cannot tell" for every copy when registry access fails (R2). Waived for 16.0.0 by Peter (rulings item 12); tracked: `.kiro/issues/2026-10-02-one-hop-upgrade-rehearsal-tracked-residuals.md`.
  - Product-token staleness: a plain `generate` decides from the product YAML's file times alone, and `--product-only` resolves from the current directory. Tracked: `.kiro/issues/2026-10-12-generate-staleness-decided-by-file-times.md`, `.kiro/issues/2026-10-03-generate-product-only-resolves-from-cwd.md`.
  - Served governance docs name `src/` files that exist in DesignerPunk's repository but not in the package (67 files across 19 docs at 15.1.0; not re-counted for these notes). Tracked: `.kiro/issues/2026-10-13-src-path-convention-for-served-governance-docs.md`.
  - `SemanticOverrideMap` is not exported from `@3fn/core/config`. Tracked: `.kiro/issues/2026-10-03-semantic-override-map-type-not-exported.md`.
- **Docs-MCP delivery gaps waived for this release** (rulings item 14): the audience banners are not delivered on the summary-first path; `get_section` can return only the opening of a fenced template; a `####` section cannot be fetched by `get_section`, and `SectionNotFound` suggestions cannot reach one. One docs-MCP PR follows the tag.

## Upgrading from 15.1.0

1. `npm install @3fn/core@16.0.0`.
2. Search your code for `input-radio-set` and `InputRadioSet(` (Swift and Kotlin), and add the group's name to each, as shown under "Breaking".
3. If you run `validate_assembly` in your own checks, re-run them: a tree with a wrong prop value now fails.
4. Run `npx designerpunk sync` in a terminal to refresh your generated agent files (the write-scope, Leonardo and Sparky changes arrive this way). It reports what it changes, if anything.
5. If you commit generated platform output, run `npx designerpunk generate` and commit the header-only change; no token value changed in this release.
6. Restart your agent session, so that the MCP servers load the new version.
7. If your own tooling calls `find_docs` with a `concept` and expects every match in one response, follow `nextCursor`; the first page holds the best 20.

**Upgrading from 15.0.0 or 14.x**: follow the 15.1.0 notes (`docs/releases/release-15.1.0.md`) and, for 14.x, the 15.0.0 notes, installing 16.0.0 at step 1, then the steps above from step 2. The one-hop rehearsal from 14.x was run for 15.0.0 and has **not** been re-run for 15.1.0 or 16.0.0.
