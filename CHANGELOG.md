# Changelog

All notable consumer-facing changes to `@3fn/core` are recorded here, one entry per release, in plain language for the people who install this package. Internal-only changes (governance, test infrastructure, spec process) are not listed — see this repository's release history (https://github.com/3fn/DesignerPunk/releases) for the full hand-authored delta if you need that detail.

This file starts with Spec 123 ("Consumer Distribution"). Earlier releases are not backfilled here.

## [16.1.0] — 2026-10-26 — Release 5 (web element properties, token-index consumers, Android interim fixes, docs MCP fixes)

This release is for building web products, with the agent layer for Claude Code and Kiro. Native onboarding is still not supported: the iOS (SwiftUI) and Android (Jetpack Compose) components and the generated Android token files are reference source, not a build input (see "Known limitations"). On web, a custom theme you register in `designerpunk.config.ts` still does not change your generated output.

This is the fifth planned entry in the plan's numbering ("Release N" labels the Nth planned entry, not a count of tags), and a minor release: no export or token was removed, and no token value changed. One shipped file pair was removed, `dist/components/core/Button-CTA/Button-CTA.refs.{js,d.ts}`, which no documented entry point exports (see "Changed"). Some things can look different from 16.0.0 and are listed under "Changed": the large Button-CTA's icon is 4px smaller on web, a checkbox now submits with its form (so a hidden-input workaround now submits its value twice), a checkbox authored `checked` stays checked when its form is reset, `find_components` marks fewer matches `strong`, and your token index and `generate` report more. `generate` also stops, and says why, where it used to write a colour reference its own output does not define. The steps are under "Upgrading from 16.0.0" at the end of this entry.

### Added

- **The Integration Guide has a new `## Walkthroughs` section: six goal-shaped guides written for you to follow with your agent beside you.** Four are available on this release (see DesignerPunk working, specify your first screen, join a teammate's design system, change a token and see it on web), and two are marked not available yet (your brand theme; building for iOS or Android, awaiting Spec 129). The walkthroughs were checked as text. The onboarding trio follows `docs/consumer/INSTALL.md`, and no 16.1.0 run opened a walkthrough, so none has been run cold.
- **The package now ships `scripts/owed-set.sh`, the query your Stacy agent uses to list the specs whose claims pass may be owed.** Run `bash node_modules/@3fn/core/scripts/owed-set.sh --specs-dir specs` (add `--adoption <file>`, a file with a line `Adopted: YYYY-MM-DD`, to set the adoption date). It only reads, and it exits 0 whatever it finds. It prints one row per spec, classed `candidate`, `closed`, `open`, `stub` or `touch-only`, then a count line. Only a `candidate` row can be owed, and it is not a verdict. Stacy's agent file names it and reaches your repo through `sync`.
- **`<button-cta>` and `<button-icon>` now have the `variant` and `onPress` properties the component schema lists.** Before, the schema served `variant` and `onPress` as properties, but the web elements had neither: `el.variant = "secondary"` set a plain JavaScript field and the button stayed primary, and `el.onPress = fn` never ran, because the elements only had a `buttonVariant` property and dispatched a `press` event. `el.variant` now reads and writes the `variant` attribute, so setting either re-renders. `buttonVariant` still works, as an alias. `el.onPress = fn` now runs `fn` on each press (click, Enter or Space); assigning again replaces the callback, and `el.onPress = null` removes it. The `press` event is unchanged. If you wire both `onPress` and a `press` listener, each runs once per press. Code written against 16.0.0 that used `buttonVariant`, the `variant` attribute or the `press` event behaves as before. Code that assigned `el.variant` or `el.onPress`, which did nothing in 16.0.0, now takes effect: check that a button you set `el.variant` on should look that way, and that a function you assigned to `onPress` is not also wired as a `press` listener, or it now runs twice.

### Changed

- **Visual change: on web, the large Button-CTA's icon is now 28px (it was 32px), and `iconBaseSizes.size125` is now `28` (it was `32`).** Both now match the `icon.size125` token (28px) and what iOS and Android already draw. `iconBaseSizes.size125` was `32`, which drew the `size200` icon, so a web large button's icon was 4px larger than on the phone. Button-CTA has no option for its icon's size, so the button's icon cannot be set back to 32px. If your own `<icon-base>` uses `iconBaseSizes.size125`, its icon is now 4px smaller; for the old 32px, use `iconBaseSizes.size200` or set `size="32"`. The accepted size `13` still draws 16px; that is unchanged here.
- **Input-Checkbox-Base and Input-Checkbox-Legal now submit with their form on web.** A checked box adds `name=value` to `FormData` (`value` defaults to `"on"`), as a native checkbox does; before, neither submitted anything. **If you added a hidden input to work around this, remove it, or the value is submitted twice.** Setting `disabled` on either has no effect: the attribute is removed so it cannot drop the value. A `<fieldset disabled>` around either still leaves it out of the submission, as for a native checkbox. Needs a browser with form-associated custom elements (Safari 16.4+). Also fixed: a user's click on `Input-Checkbox-Legal` is no longer refused as a pre-check.
- **`get_token_consumers` now finds DesignerPunk's components, and finds consumers of primitive and component tokens as well as semantic ones.** Before, it answered only for semantic tokens and, in a repo created with `init`, only for components in your own repo. A component that declared a token under an old or misspelled name was missed as well: 97 of the 532 token declarations in DesignerPunk's component schemas named no token (55 distinct names), among them `color.error.strong`, `radiusFull` and `blend.iconLighter`. Those schemas now use the token names in the token index, and the token index lists consumers on primitive and component tokens as well as semantic ones. In a repo created with `init`, the consumers now include DesignerPunk's components as well as your own; where one of yours declares the same name as one of DesignerPunk's, yours is counted and DesignerPunk's is not. **Run `npx designerpunk generate` after upgrading, and after every later upgrade**: your token index is rebuilt then, not at install, and which of DesignerPunk's components it counts depends on the version you have installed. If one of DesignerPunk's components declares a token your token source no longer has, `generate` now names it in a warning: that component reads a CSS variable or constant your generated output no longer has. `generate` also warns about any of your own schemas that declare a token name your token source does not have (the name must match exactly, case included). Neither warning stops `generate`.
- **Your token index now holds DesignerPunk's own component tokens**, for example `avatar.size.md` and `buttonicon.size.medium`, in a repo created with `init` and in package mode. So `get_token_details` finds them, and `get_token_consumers` lists the components whose schemas declare them. `generate` takes them from the installed package's own token index, with DesignerPunk's references and platform names, for every DesignerPunk component you have not replaced: where one of your components declares the same name as one of DesignerPunk's, its tokens are not taken, and your own token source defines them. A component token in your own token source keeps its entry. **Your generated platform output does not change**: these tokens are defined by `@3fn/core/component-tokens.css`, which you keep importing. **Each of these entries records the package version it came from** (`source: { package: '@3fn/core', version: … }`); an entry without `source` came from your own token source. They are as current as your last `generate`, so after an upgrade `sync` now tells you when your token index is behind the installed package, and counts running `generate` as still to do. Every component-token entry made from a component's own token file also names that component (`definedBy`). The one-line note `generate` printed about these tokens is gone.
- **`validate --product-tokens` accepts a product token whose `ref` names one of DesignerPunk's component tokens** (for example `avatar.size.md`), because those tokens are now in your token index after `generate`. Before, it reported the reference as not in the token index, although the CSS variable is on the page.
- **In package mode** (a `designerpunk.config.ts` with no `tokenSource`), `generate` now counts DesignerPunk's components as consumers and no longer reads a `src/components/core` folder in your repo, so its token index counts the components the Application MCP serves.
- **Internal: Button-CTA's `ButtonCTATokens` and `getButtonCTAMinWidth` are removed.** They were a table of the button's minimum widths that no platform read, and the package's `exports` never made them reachable, so no install that imports only the documented entry points is affected. (In 16.0.0 the built file shipped under `dist`, because `files` includes it, but `exports` blocked its import path; in 16.1.0 the file is gone.) Button-CTA's minimum widths are unchanged (56, 72 and 80); the web and iOS components now read the `sizing` tokens `size700`, `size900` and `size1000` instead of the literal numbers, as the Android component already did.
- **Theme text in the docs and the agent charters now says what `generate` emits.** `data-theme` goes on `<html>` and themes the whole page, because the one emitted theme block, `:root[data-theme="wcag"]`, matches only the document root; whether an element can theme its own subtree is not decided yet. A theme you register in `designerpunk.config.ts` is read and listed as "registered, not applied yet", and the Swift and Kotlin theme types are not generated yet (Spec 129 plans them). The Sparky and Ada charters, `governance/Token-Governance.md`, `Token-Quick-Reference.md`, `Token-Semantic-Structure.md` and `Rosetta-System-Architecture.md` were corrected to match. No generated output changes.
- **The three MCP servers now bundle newer versions of four libraries that had published fixes.** The servers in `dist/mcp/` inline their dependencies, so a consumer's `npm audit` cannot see them (it reads the dependency tree, and inlined code is not in it). Bundled before → now: `@modelcontextprotocol/sdk` 1.29.0 → 1.32.2 (all three bundles; the stdio server modules only, none of its HTTP, OAuth or client modules), `fast-uri` 3.1.3 → 3.1.9 (all three), `js-yaml` 4.2.0 → 4.3.2 (the Application and Product bundles; the Docs bundle has none) and `zod` 4.3.6 → 4.6.7 (all three; the fix for GHSA-mrhx-c7xc-m3w5, a high-severity advisory in which Zod can exhaust memory while validating oversized constrained collections). No tool, argument or output changed.

- **Checkbox form reset now restores the authored state.** A checkbox authored `checked` stays checked when its form is reset, as the contract always said; earlier releases unchecked it. "Authored" means the state when the element first connected, whether it came from a `checked` attribute or a `checked` property set before it was inserted; a later `setAttribute('checked')` is state, not a new default (a native checkbox differs here, and both READMEs say so). Input-Checkbox-Base also restores an `indeterminate` it was authored with. Input-Checkbox-Legal with `requiresExplicitConsent` (the default) still resets to unchecked, because a pre-check it refused is never authored. Neither fires `change`, `onChange` or `consent-change` on reset, as a native reset does.
- **Nav-SegmentedChoice-Base's tabs now set `ariaControlsElements` to your panels on web.** With an `id`, each tab refers to your `[id]-panel-[value]` element through `ariaControlsElements`, in the document or in an enclosing shadow root, and follows the panel as it is added, removed or replaced. The `aria-controls` attribute alone could not cross the component's shadow root, so before this the reference resolved to no element. Checked in Chromium 152: the reference is set and read back. Not observed: whether a screen reader announces it, and Safari and Firefox were not run. The component's `accessibility_aria_controls` contract says the same: where the browser has `ariaControlsElements` the element reference is set and the `aria-controls` attribute reads empty; where it has not, the attribute is set and no tab-to-panel association is provided.
- **The Application MCP says when `COMPONENTS_DIR` points nowhere.** If the variable names a folder that does not exist, health reads `degraded`, the boot log carries a line saying your own components are not indexed and only DesignerPunk's are, and `get_component_full` and `get_component_summary` carry the same warning first in `warnings`. Before, the server read `healthy` over DesignerPunk's components alone. A missing default folder (no variable set) is not a warning. This reports the problem; it does not repair a config that still points at a pre-123 folder.
- **The docs MCP carries each document's audience banner and reaches more of a document.** `get_document_summary` now returns an `audienceBanner` on the documents that have one, and `get_section` returns it too (about 480 bytes more per call on those documents; others pay nothing), so an agent that goes straight to a section still sees who the document is for. A `##` heading inside a fenced template no longer ends the section around it. A `####` section can now be fetched by its own id (the first `####` under section `s13` is `s13.1`); the ids that existed do not change. A "section not found" answer now also suggests up to 10 matching `###` and `####` headings after its `##` list. The server's logs go to the folder named by `DESIGNERPUNK_DOCS_MCP_LOGS` if you set it, and otherwise to a folder under your system temp directory; before, it created `mcp-server/logs` in whatever folder it was started from.
- **`find_components` marks fewer matches `strong`.** With `keyword`, a component whose only match is a word in its `purpose` (or a concept suffix) now reads `partial`; `strong` needs the keyword to match the component's name or family, or at least two salient words covering more than half of the query. The ranking rule is unchanged, but it sorts by tier first, so a result that moved to `partial` now ranks below the results that stayed `strong`: for "loading", Progress-Bar-Base, the closest match, went from first to fourth of four tied `partial` results. On the queries this was measured against, the tier rule moved 19 results from `strong` to `partial` and none up, and the Button-CTA purpose rewrite below moved one more. Button-CTA's `purpose` now says what it is ("Provide a prominent call-to-action button for primary user actions.") and not where it is used, so a query like "confirm sheet or dialog" no longer reads it as `strong`. On new queries, `strong` can still cover every row (the 16.1.0 trio saw 8 of 8 and 9 of 9); read `readiness` and `viability` before acting on it.
- **The deprecated disabled blend is no longer described as "scheduled for removal in the next major version".** That text was wrong: no removal was ever scheduled. `blend.disabledDesaturate` and the `disabledColor()`/`disabledBlend()` wrappers are still deprecated and still present; keep them out of new code. The corrected text is in the token's description (so also in `DesignTokens.dtcg.json` and the Figma export, if you generate them), the wrappers' deprecation messages, and `Token-Family-Blend.md` and `Token-Family-Color.md`. Text only: no token value changed.
- **Small corrections in documents the docs MCP serves, and in your agents' charters.** Docs and charters that taught token names that are not keys in the token index (for example `borderDefault`, where the key is `border.default`) now name the keys, in 26 governance docs, Core Goals, the Systems Overview and the component YAML the Application MCP serves; `Token-Governance.md`'s component-token pattern now matches the code (`<component>.<property>`, numeric families only, no colour family). Other token docs were not checked for such names yet (tracked: `.kiro/issues/2026-10-25-token-docs-unvetted-name-hits.md`); 48 relative links that pointed at the wrong depth now resolve; the always-loaded overviews carry corrected counts and describe the Product MCP as built; Icon-Base's schema, README and error message now say that the accepted size `13` draws 16px; and one sentence in `Process-Spec-Planning.md` no longer tells a consumer agent that a parser exists that the package does not ship. None of them asks anything of you. The charter lines reach your repo through `sync`.
- **Your agents now follow one token-selection order, and Core Goals points to it.** Core Goals (`designerpunk-core-goals.md` in your agent files) carried its own numbered order, which contradicted Token Governance's. It now says the one order is Token Governance § "Token Selection Matrix" and how to fetch it. In that order, a component's own token comes first inside the component it belongs to, and using it there for the property it was made for needs no approval; any other use of a component token still does. A missing token is a checkpoint with you, never an invented or hard-coded value. The Component Token Construction Rule moved from Core Goals to Token Governance § "Token Creation Governance". Your Ada and Lina agent files point to the matrix in the same way, and their changed lines were re-confirmed and re-signed. They reach your repo through `sync`. This is a governance change applied by ballot (`2026-10-25-token-selection-order-one-rule`, #480 and #491); no token value and no generated platform output changed.
- **Button-CTA's served guidance now says that on the web it does not submit a form by itself.** `get_component_full`, `validate_assembly`'s `form-needs-submit-action` warning and the browser guide name the wiring: call `form.requestSubmit()` from `press`, and handle Enter in the page. The element's behaviour is unchanged.
- **`generate` now stops when a semantic colour points at a colour it does not emit.** Colour primitives are emitted from the installed package's palette, not from your copy (see "Known limitations"). So a colour primitive you added to your copy reached no platform file, and a semantic token pointed at it produced output that names a colour it does not define (on web, the colour stopped applying), with exit 0. `generate` now checks each semantic colour reference against the colours it emits and, if one is missing, stops before writing anything, naming the token, the colour and the reason. A colour you added only under `color/primitives/` already stopped `generate`, with a message saying the colour did not exist; that message now says why too.

### Fixed

- **Android Button-CTA and Avatar-Base convert sizing tokens to `Dp`, and three components stop calling `.dp` on values that are already `Dp`.** On Android the generated sizing tokens (`DesignTokens.size_*`) are `Float`, while spacing and radius are `Dp`. Button-CTA (height, minimum width, and the large size's touch target) and Avatar-Base (all six sizes) passed them to `Dp` parameters with no conversion, which Kotlin rejects; each of the 13 reads now converts with `.dp`, and Button-CTA now imports `Dp`, which it used without importing. This was found and fixed by reading the Kotlin: no Android build has been run. The Android components are still reference source, not a build input, and do not compile as shipped for other recorded reasons (the generated `DesignTokens.android.kt` has no `import` lines, for one). A later release is planned to generate sizing as `Dp`; when it does, these `.dp` calls are removed, and Android code of your own that adds `.dp` to a `DesignTokens.size_*` value will need the same change. The same pass removed `.dp` from 16 places where the value was already a `Dp` (the border widths in Button-VerticalList-Item's `VisualStateStyles`, the touch target in Nav-Header-Base, and the tab padding, minimum size and icon size in Nav-TabBar-Base), which Kotlin also rejects; a guard test now checks both.
- **`sync`'s upgrade report now says what is true.** It no longer ends with "Everything DesignerPunk manages is up to date" while the same report still offers a migration or a repair, and a run that applies something now lists, after the report, what it applied and what is left. When judging pre-123 component copies, it checks the `@3fn/core` you have installed before fetching anything, reports a refused registry token once, as a login problem (not once per copy), and names a long list of versions in one short clause. If your registry lists no version as old as your repo's last sync, a copy that matches nothing is now left in place, not called your fork. That does not cover every older copy: one made before 13.0.0, in a repo last synced at 13.0.0 or later or with no old `.kiro/sync-manifest.json`, can still read as a fork once the old GitHub Packages line is gone from `.npmrc`, so renew a refused GitHub token before removing that line. It also says the old `.kiro/sync-manifest.json` is converted and kept, which is what it always did, instead of saying it moves.
- **`generate` no longer suggests `--product-only` when you have no product tokens.** When the system tokens failed to generate and the product tokens did not, `generate` printed "Tip: Use --product-only …" even in a repo with no `productTokens` configured. It now prints the tip only when `productTokens` is set. The exit code is unchanged.

### Known limitations in this release

- The 16.0.0 limitation "In a repo created with `init`, `get_token_consumers` counts only your own components" no longer applies, and DesignerPunk's own component tokens are now in your token index (see "Changed").
- `get_token_consumers` lists the components whose schemas declare a token; it does not scan platform code. DesignerPunk's component schemas now declare the tokens a scan of their web, iOS and Android code found them reading (229 declarations were added in this release, for example Button-CTA's `shadow.hover` and `tapAreaMinimum`; two native reads name tokens the token index does not hold and are recorded for a fix: `.kiro/issues/2026-10-25-native-reads-of-names-the-theme-does-not-hold.md`). The scan is not committed, and no check yet fails when a component reads a token its schema does not declare, so a read added later can be missing from the list until the schema is updated. The tool's description now says what it answers from. Tracked: `.kiro/issues/archive/2026-10-23-schema-tokens-declared-vs-read-completeness.md` (a check that fails when a read has no declaration is a recorded follow-up, not in this release).
- **Part of the token source `init` copied into your repo is still not read.** `generate` takes the colour palette, the dark and WCAG override maps, the motion and layering tokens, the whole DTCG/Figma export and a few other parts of the token source from the installed package, so editing those parts of your copy does not change your output yet; spacing and the other non-colour primitives, and your semantic references, are read from your copy. A colour you add to your copy is not emitted either, so do not point a semantic token at one: `generate` now stops before writing anything and says why (see "Changed"). Point semantic tokens only at colours already in the palette `init` copied. Tracked: `.kiro/issues/archive/2026-10-25-generate-passes-semantic-references-to-unemitted-primitives.md`. The install guide (`docs/consumer/INSTALL.md`, § 4, "Your language vs our updating surface") has the full list. This is unchanged from 16.0.0. Planned in Spec 129; tracked: `.kiro/issues/2026-10-15-123-palette-read-from-package.md`.
- **The Android components and the generated Android token files are reference source, not compile-verified.** No Android build has been run against them, and they are known not to compile as shipped: `DesignTokens.android.kt` has no `import` lines, has two bare text lines inside its `object`, constructs a `Typography` type nothing defines and carries CSS-syntax `oklch(…)` lines; several components read tokens at the wrong unit type (for example `fontSize`, which is generated as `Dp`); and `Input-Text-Base` declares token constants with no value. Do not start an Android product from this source. These are recorded and planned for Spec 129, whose first task is a build check that actually compiles the Android output; until it runs, nothing here has been proven to build.
- **Several web elements' served property and event names do not yet match what the elements expose.** Button-CTA and Button-Icon now have `variant` and `onPress`; a sweep of every other web element's served names against its code is planned after this release. Separately, the text inputs (Input-Text-Base and its Email, Password and PhoneNumber variants) are not form-associated on web: they do not add their value to `FormData`, and no contract promises that they do. The two checkboxes are the only form controls changed here, and their submission was checked in Chromium, not in Safari or Firefox. Tracked: `.kiro/issues/2026-10-20-web-element-api-and-form-participation.md` and `.kiro/issues/2026-10-25-web-elements-served-prop-sweep.md`.
- **On web, Button-CTA does not submit a form by itself.** It is served as a form's submit action, but the web element is not form-associated: its inner button is `type="button"`, so a click submits nothing, and a form with more than one text field no longer submits on Enter once its native submit button is replaced. Wire it as the browser guide's § "ButtonCTA" shows: call `form.requestSubmit()` from `press`, and handle Enter in the page. A `type` prop and form association are planned in a spec. Tracked: `.kiro/issues/2026-10-20-web-element-api-and-form-participation.md` (E8).
- **`validate_assembly`'s empty `accessibility` list covers three checks only**: a form's accessible name, a form's submit action and a page's accessible name. It does not check for an interactive control inside another (a pressable card holding a button passes), and it skips props it cannot read as a list of values, Icon-Base's `name` among them, so an unknown icon name passes. The tool's description names the three checks; the result does not say what it skipped. Tracked: `.kiro/issues/2026-10-25-validate-assembly-empty-result-overstates-coverage.md`.
- **After an upgrade, the Application MCP reads `healthy` over a token index that is behind.** Until you run `npx designerpunk generate`, `token-index/components.yaml` still holds DesignerPunk's component tokens from the version you had: `get_component_health` says `healthy` with no warning, and `get_token_consumers` answers from the old merge. Each such entry carries its own `source.version`, and `sync` tells you the index is behind (see "Changed"); the MCP does not. Run `generate` after every upgrade. Tracked: `.kiro/issues/2026-10-25-application-mcp-stale-package-token-version-warning.md`.
- **Every `generate` prints one warning about DesignerPunk's own shadow colours**: "15 shadow token(s) reference shadow colour primitive(s) that no platform file defines (shadowBlack100, shadowBlue100). This is a known DesignerPunk defect, not a problem in your token source; generate continues." Nothing is asked of you. The defect is recorded and planned for Spec 129, and the warning is removed when it is fixed. Tracked: `.kiro/issues/2026-10-24-shadow-color-primitives-emitted-on-no-platform.md`.
- On Kiro, our onboarding tests ran only the Sparky and Leonardo agents, on a preview of this release. The Thurgood and Stacy agent files changed in this release and have not been run (that run is re-queued for November), and Ada, Lina, Kenya and Data were not run on Kiro (Ada and Lina were run on Claude Code). The Ada and Lina agent files and the Core Goals file changed after that preview, and no run has seen them on either harness.
- The known limitations listed for 15.1.0 and 16.0.0 and not restated above were not re-measured for this release and are assumed to still apply: `validate`'s mathematical-relationships check fails on unmodified token source, and `--migrate-components` reports "cannot tell" when your registry access fails (its report is shorter and names a registry login problem once; see "Fixed"). The readiness half was measured: the Application MCP reads 32 of DesignerPunk's 34 components as `scaffold` on iOS and Android, and 4 of 34 on web. On web, Nav-Header-App is still `scaffold`, and the starter screen `init` writes uses it; check `readiness` before building on it.

### Upgrading from 16.0.0

1. `npm install @3fn/core@16.1.0`.
2. Run `npx designerpunk sync` in a terminal to refresh your generated agent files (the charter lines in "Changed" and Stacy's `owed-set.sh` pointer reach you this way). It reports what it changes, and now says what it applied and what is left.
3. Run `npx designerpunk generate`. Your token index is rebuilt then, not at install: it now holds DesignerPunk's component tokens and lists consumers on primitive and component tokens. If it prints a warning about a component token your token source no longer has, or about one of your own schemas, read it; neither stops `generate`. It also prints one warning about DesignerPunk's own shadow colours on every run (see "Known limitations"). If it stops because a semantic colour points at a colour it does not emit, point that token at a palette colour (see "Changed"). If you commit generated platform output, commit what changes: the version number in each file that carries one (the Figma export carries none) and, in `DesignTokens.dtcg.json` and the Figma export if you generate it, the description text of `blend.disabledDesaturate`. No token value changed in this release.
4. If you added a hidden input to make a checkbox submit with its form, remove it (see "Changed"). If something in your page relied on a form reset unchecking a checkbox that is authored `checked`, it no longer does.
5. If your page uses the large Button-CTA on web, its icon is now 28px (it was 32px), and Button-CTA has no option to set it back. If your own code sizes an `<icon-base>` with `iconBaseSizes.size125` and you want 32px, use `iconBaseSizes.size200` (see "Changed").
6. Restart your agent session, so that the MCP servers load the new version (the install guide's rule for any package update).

## [16.0.0] — 2026-10-16 — Release 4 (the `Input-Radio-Set` group name, install-guide corrections, `init` off a terminal)

This release is ready for building web products, with the agent layer for Claude Code and Kiro. Native onboarding is not supported yet: the iOS (SwiftUI) and Android (Jetpack Compose) components ship as reference source, not a build input, so don't start a native product on this release. On web, a custom theme you register in `designerpunk.config.ts` does not change your generated output yet; light and dark mode work.

This is the fourth planned entry in the plan's numbering ("Release N" labels the Nth planned entry, not a count of tags). **It is a major release for one reason: `Input-Radio-Set` now requires a property it did not have** (see "Breaking"). A call site written for 15.1.0 is a compile error in typed TypeScript (and on iOS and Android, if you build the native reference source), and on web it renders a radio group with no accessible name. Nothing else a 15.1.0 install relies on was removed: no export, no shipped file, no token. No token value changed. Two other changes can turn something that passed on 15.1.0 into a failure, and they are listed under "Changed" because each only reports or pages what was already there: `validate_assembly` now fails a tree with a wrong prop value, and `find_docs` in concept mode returns one page of results at a time. Also under "Changed": Button-CTA's contract no longer claims a loading state it never had, your agents' write scope reads differently, and the install guide says more. The steps are under "Upgrading from 15.1.0" at the end of this entry.

### Breaking

- **`Input-Radio-Set` now requires a name for the radio group.** A radio group needs an accessible name, so that a screen reader announces what the choice is ("Theme", "Plan") and not only that it is a radio group (WCAG 4.1.2). The name is a new required property, `accessibilityLabel`. It is not drawn on screen: show the visible question as your own text, and pass the same words here. One edit per platform:
  - **Web:** add the attribute `accessibility-label` to `<input-radio-set>`, for example `<input-radio-set accessibility-label="Theme" …>`. From script, set the property: `radioSet.accessibilityLabel = "Theme"`. It becomes the `aria-label` of the group's `role="radiogroup"`.
  - **SwiftUI:** pass `accessibilityLabel:` as the second argument, right after `selectedValue:`, for example `InputRadioSet(selectedValue: $plan, accessibilityLabel: "Plan") { … }`. It replaces the fixed "Radio group" label the component used to announce, which named the role and not the choice.
  - **Jetpack Compose:** pass the named parameter `accessibilityLabel = "Plan"` (a `String`, with no default), for example `InputRadioSet(selectedValue = plan, onSelectionChange = { plan = it }, accessibilityLabel = "Plan") { … }`.

  **If you do not update your call sites:** on iOS, on Android and in typed TypeScript, a missing label is a compile error. (Native source is reference source in this release, so you meet that error only if you build it.) On web it is not a build error: the group renders with no accessible name, and a development warning in the console names the missing `accessibility-label` attribute. An empty or whitespace-only value counts as missing, so `""` does not satisfy it. The Application MCP's `validate_assembly` also warns about a tree that leaves it out, and the form experience patterns (`multi-section-form`, `view-edit-screen`) now tell your agent to supply the group name.

### Changed

- **`validate_assembly` now checks prop values against each component's schema.** A wrong value for a known prop is now an error that names the prop and its allowed values: for example Button-CTA `size: "md"`, where the schema allows `small`, `medium` or `large`, or a colour prop that is not a real colour token. Before this, such a tree passed. **A tree that passed on 15.1.0 can now fail.**
- **`validate_assembly` also warns** about a prop name the component's schema does not list, and about a required prop that is missing (callback props are exempt). A warning does not fail the tree; this is how an `Input-Radio-Set` without `accessibilityLabel` is flagged. Not checked: data bindings (`"{Domain.field}"`), functions, objects, `IconName` values and free-form strings.
- **`find_docs` in concept mode now returns one page of results.** It returns 20 matches by default (`limit` raises it, up to 100) and a `nextCursor` when more remain; pass it back as `cursor` for the next page. Pages are cut after ranking, so the first page holds the best matches. Before, concept mode ignored `limit` and `cursor` and returned every match in one response. If your own tooling calls `find_docs` with a `concept` and expects every match at once, follow `nextCursor`. List mode is unchanged.
- **`find_components` says what its filter results are.** Without `keyword`, the `context` and `category` filters are exact constraints: their rows carry no `matchConfidence`, `matchedOn` or `rank`, and they come back in name order. Only the tool's description changed; its results did not.
- **The install guide's restart step says what each agent tool asks.** On the founding and joining paths, `docs/consumer/INSTALL.md` (and the Integration Guide it is generated from) now says that Claude Code asks you to trust the folder and then to enable DesignerPunk's three MCP servers, and that you accept both; Kiro asks nothing. The README's "Getting Started" steps say the same. Before, they said only "approve DesignerPunk's MCP servers if asked". The reference path (no `init`) is unchanged.
- **The install guide covers more of what you meet on the way in.** `docs/consumer/INSTALL.md` (and the Integration Guide it is generated from) now says: which parts of your token source `generate` does not read yet (see "Known limitations"); how to keep `init` from breaking a TypeScript project's own build (exclude `src/tokens/**` and `src/components/**` from your `tsconfig.json`, and keep `output` outside your build's `dist/`); how a web page with no build step loads the components, and that it must be served over local HTTP, not opened as a file; what a joining teammate commits after `attach` (and that `.claude/settings.local.json` stays uncommitted), and why a join runs `generate`; and, for upgrades from 14.x, that the report `sync` prints before applying shows the state before the conversion, and that the old manifest is kept, not moved. The browser distribution guide now tells you to link your own `DesignTokens.web.css` in place of the base `tokens.css`, and its token list and custom-style example now name CSS custom properties that exist (six of the names they used did not).
- **Button-CTA's contract no longer claims a loading state.** Its `contracts.yaml` (now version 2.0.0) listed `state_loading` as a required contract on web, iOS and Android, but none of the three implementations has a loading state: no loading property, no spinner, no busy announcement. The Application MCP no longer lists it for Button-CTA. A loading state is planned for 16.x. If you or your agent planned on `state_loading` for an in-flight action, show the progress yourself (for example an indeterminate `Progress-Bar-Base` beside the button) and ignore repeat presses in your `onPress` handler until the action settles.
- **Your agents' write scope now names a pre-approved set and tells the agent to ask before writing elsewhere.** Each generated agent's "Write scope" section used to say the agent may create or modify files only under its listed paths and must treat every other path as read-only, so an agent could refuse work its role needs, even after you said yes in the session (in DesignerPunk's own Kiro runs, Sparky refused to create a file at `src/hello.ts`, with and without a yes given in the session; a screen under `src/` meets the same sentence, so Sparky would refuse the screen code a Leonardo spec asks for). It now says the listed paths are pre-approved, and that for any other path the agent asks you first and writes there only after you confirm in that session. Kiro may also show its own permission prompt for such a write; Claude Code may not, so your confirmation is the check. This reaches your repo through `sync`, as regenerated agent files.
- **Leonardo writes screen specifications where the Product MCP finds them.** `product/**` is now among his pre-approved paths, and his "Specify the Screen" step says where a screen goes: `product/experience-map/pages/`, with the Integration Guide's "Product Data Directory" section for the full tree. Before, his only writable path was `specs/**`, so a screen he specified landed where `find_screens` never looks. Sparky's instructions now tell him to link your own `DesignTokens.web.css`, which `generate` writes, in place of DesignerPunk's base `tokens.css`, alongside the component-token stylesheet the install guide names. Both reach your repo through `sync`.
- **Small corrections in documents the docs MCP serves.** An example link in `Process-Cross-Reference-Standards.md` no longer names a developer's home directory; `Token-Family-Opacity.md` notes when its "Disabled States" section was last revised; and `classification-map.md` changed with DesignerPunk's own release process. None of them asks anything of you.

### Fixed

- **`init` stops with an error where no terminal is attached, instead of waiting forever, and a `.gitignore` it creates now ignores `node_modules/`.** Run from an agent's shell or from CI without `--name` and `--abbreviation`, `init` used to wait for an answer no one could give. It now exits at once with a message that names both flags, and writes nothing: pass both (`--name=<name>` works as well as `--name <name>`). When `init` creates your `.gitignore`, it now writes `node_modules/` above DesignerPunk's block, as your own line that `sync` never changes; an existing `.gitignore` is left as it is, so check that yours ignores `node_modules/`. `npx designerpunk --help` now says the two flags are required where no terminal is attached, lists `--re-scaffold` and `--yes`, no longer lists `--skip-components` (it does nothing; `init` still accepts it), and names the install guide, as `init`'s closing output now does. When `init` refuses because the repo already has a design system, its restart step now says what Claude Code and Kiro ask.

### Known limitations in this release

- **Part of the token source `init` copied into your repo is not read yet.** `generate` takes the following from the installed package, so editing them in your copy does not change your output yet: the colour palette; the dark and WCAG override maps; the opacity values that colours with transparency are built from; the motion tokens (duration, easing and scale) and the layering tokens; the font-size and line-height values that icon sizes are calculated from (your own font-size and line-height tokens are still read from your copy); and the whole DTCG/Figma export. Spacing and the other non-colour primitives, and your semantic references, are read from your copy. This was already true in 15.0.0 and 15.1.0; it is stated here for the first time. The install guide's "yours wholesale" sentence is corrected to match.
- In a repo created with `init`, `get_token_consumers` counts only your own components; DesignerPunk's components are not counted yet.
- **`blend.disabledDesaturate` and the `disabledColor()`/`disabledBlend()` wrappers are still deprecated, not removed.** Their deprecation text says they are scheduled for removal in the next major version: the token's description (in `BlendTokens.js` and the DTCG and Figma exports), the wrappers' deprecation messages, and the docs MCP's `Token-Family-Blend.md` and `Token-Family-Color.md`. 16.0.0 is a major release and does not remove them, and no release is scheduled to; keep them out of new code. That text is corrected after this release; tracked: `.kiro/issues/2026-10-16-blend-deprecation-next-major-doc-correction.md`.
- The known limitations listed for 15.1.0 still apply: `validate`'s mathematical-relationships check fails on unmodified token source; the Application MCP reads most of DesignerPunk's iOS and Android implementations as `scaffold`; and `--migrate-components` reports "cannot tell" when your registry access fails.

### Upgrading from 15.1.0

1. `npm install @3fn/core@16.0.0`.
2. Search your code for `input-radio-set` and `InputRadioSet(` (Swift and Kotlin), and add the group's name to each, as shown under "Breaking".
3. If you run `validate_assembly` in your own checks, re-run them: a tree with a wrong prop value now fails (see "Changed").
4. Run `npx designerpunk sync` in a terminal to refresh your generated agent files. It reports what it changes, if anything.
5. If you commit generated platform output, run `npx designerpunk generate` and commit what changes: the version number in each file, and, in `DesignTokens.dtcg.json`, one line of text, the deprecation reason on `blend.disabledDesaturate` (#368). No token value changed in this release.
6. Restart your agent session, so that the MCP servers load the new version (the install guide's rule for any package update).
7. If your own tooling calls `find_docs` with a `concept` and expects every match in one response, follow `nextCursor`; the first page holds the best 20.

## [15.0.0] — 2026-10-02

**This is a breaking (major) release for anyone running an earlier `@3fn/core`.** It ships, as one release, what was planned as two: the distribution substrate and the generated agent layer. To upgrade a 14.x install, see "Upgrading from 14.x" at the end of this entry. **In 15.0.0, the web path and the generated agent layer are ready; native (iOS/Android) onboarding is not supported yet** (see "Known limitations").

### Breaking

- **`init` no longer copies `.kiro/agents/`, `.kiro/steering/`, `governance/`, `src/types` or `src/components/core` into your repo.** It creates an empty `src/components/` for your own components and generates DesignerPunk's agent layer for one target (see "Added"). Token types are imported from `@3fn/core/types`; DesignerPunk's own components stay in the package. The MCP servers serve DesignerPunk's docs from the installed package.
- **`src/` no longer ships wholesale.** The package ships only the source files it still needs: the token source `init` copies, the files that token source imports, the iOS and Android component and blend sources, and a small declared set of styles, fonts and component metadata.
- **No longer in the package: `designerpunk.config.ts`, `product-template/`, the steward agent prompts (`.kiro/agents/`), and the full `.kiro/steering/` folder.** In place of the steering folder the package ships, by name, the eight identity documents the generated agent layer reads.
- **The Inter font is removed: `@3fn/core/fonts/inter.css` no longer resolves**, and the Inter font files no longer ship. Drop the import, or use `@3fn/core/fonts/rajdhani.css`, `figtree.css` or `commit-mono.css`.

Their dark-mode values were corrected for contrast, which makes them theme-varying, and the native files do not emit theme-varying colours (see "Known limitations"). If your native code references them, keep your 14.1.0 values for these four. The web CSS still carries all four.
- **`init` now refuses to run against a born, partial, or package-mode repository**, printing a named error instead of silently re-copying or half-copying files. `--re-scaffold` lists every file it would re-add before writing anything.
- **`generate` now refuses to run in a half-set-up repo** (for example, a config file whose `tokenSource` points at no token tree), printing a named error that says what is missing, instead of guessing from the current directory.
- **`sync` no longer refreshes your token tier, your `src/types`, or your pre-existing component copies.** Once `init` has copied your tokens into your repo, they are yours — DesignerPunk's own token updates never flow back into them again. `sync` now manages only what DesignerPunk itself still owns: its MCP configuration keys, and the generated agent files for the targets you have attached.
- **`sync --force` and `--accept-all` are retired** (they print a notice and are ignored). `sync` now prints its full report before changing anything: run from a script or CI (no terminal), it writes nothing unless you pass `--apply`; at a terminal it asks once. A file you edited is overwritten only with `--overwrite <path>`, and a file you deleted is restored only with `--restore <path>`.
- **The sync manifest moved** from `.kiro/sync-manifest.json` to `designerpunk.manifest.json` at the repo root. `sync` converts the old file and leaves a one-line pointer in it for this release. Commit the new file.
- **A `tsconfig.test.json` written by an earlier `init` no longer resolves**: it pinned `@3fn/core` subpaths to raw `src/` files, several of which no longer ship. `sync` offers `--repair-tsconfig` to remove just those entries (and `--repair-npmrc` for an old `.npmrc` GitHub Packages pin).
- **Component-copy migration, opt-in**: if you installed before this release, `sync --migrate-components` judges each of your existing component copies against what DesignerPunk actually shipped in each version up to the one you have installed, and can relocate your own edits and remove copies you never touched. Nothing changes without the flag; undecidable cases are reported as "cannot tell" with an explanation, never guessed.

### Added

- **A generated agent layer.** `init` generates DesignerPunk's agents for your agent tool instead of copying prompt files into your repo. It generates the agent definitions, the always-loaded identity files, and the MCP configuration and approvals, for one target: Claude Code (`--target=cc`, the default) or Kiro (`--target=kiro`).
- **`npx designerpunk attach --target=<cc|kiro>`** adds a target to a repo: a second agent tool, or a repo that `init` did not create. **`attach --reference`** sets up only the MCP configuration and approvals. Use it to read DesignerPunk's docs and components without setting up a design system.
- **`sync --migrate-legacy`**, offered only together with `attach`. It removes the agent, steering and governance files that an earlier `init` copied into your repo, then attaches the generated layer, in the same run. Copies you edited stay on disk as yours and are no longer tracked. Nothing changes unless you pass the flag.
- **Generation warns instead of failing when the installed package is missing a member.** If a document, identity file or tool that an agent expects is missing from the installed package, that agent is generated without it. A warning names what is missing and ends: "If a clean reinstall (remove node_modules, then npm install) does not restore it, the package you installed does not contain it." The command still exits 0.
- **The generator ships compiled** (`dist/generator/`), so generating agents needs no TypeScript runtime.
- **`generate` warns about a `tokens.ts` / `*.tokens.ts` file that exports no `defineComponentTokens` value** — usually a plain reference map that should not wear that filename.
- **`@3fn/core/types` exports the `Oklch` type.**
- **The application MCP server indexes your own `src/components/` alongside DesignerPunk's**, and reindexes when your components change. Its `get_token_details` gains a `themeResolutions.dark` field.

### Changed

- **`sync` keeps the generated agent files up to date** for the targets you have attached.
- **`sync`'s MCP-key management is now key-grained, not whole-file.** A config key DesignerPunk owns (in `.kiro/settings/mcp.json`, `.mcp.json`, or `.claude/settings.json`) is compared by its parsed value, so your own keys and rules living in the same file are left untouched. If none of DesignerPunk's keys changed, the file isn't rewritten at all.
- **Both harnesses' MCP scaffolds (Kiro and Claude Code) now auto-approve exactly the tools each server marks read-only** — generated at build time from each server's own tool registrations, not a hand-maintained list. (The previous static list was already out of date: it was missing an approval for the main discovery tool and had one for a tool no server provides.) An existing install is not corrected automatically: if `sync` lists an approval under "Removed from package", it leaves it in place — remove it yourself.
- **A third MCP server entry, `designerpunk-product`, is now scaffolded** alongside the existing docs and application servers.
- **`sync` now reports two new seams instead of silently drifting**: a *name contract* (which token names DesignerPunk's web components reference, checked against your own generated web CSS) and a *type contract* (what changed in the public token type surface since your last sync). Neither writes your tokens for you — they tell you what to look at.
- **The Integration Guide** now teaches `attach` in its "Set up agent prompts" step, says plainly that native onboarding is not supported in this version, distinguishes DesignerPunk's base web CSS from your own generated CSS, and points its "Upgrading" section at this release's upgrade path.
- **The published tarball is meaningfully smaller** (about 6.4MB packed, down from about 8.4MB in 14.1.0).

### Fixed

- **DTCG and Figma exports now read the same OKLCH colour source as CSS, Swift and Kotlin**, resolving the colour divergence disclosed as a known issue in 14.1.0; dark-mode values now reach the Figma export.
- **Contrast corrections (WCAG AA)**: `color.feedback.success.text` (green500 light, green300 dark) and the dark-mode text hierarchy (`color.text.default`, `.muted`, `.subtle`). In an existing install, the light-mode change is in the token source, so it does not reach the token tier you already copied. The dark-mode and WCAG values come from the installed package on your next `generate`, so an existing install picks those up.
- **`generate` no longer crashes with a stack trace when one of your component-token files declares a token in the wrong family's `defineComponentTokens()` call.** It stops with one message that names the file and the fix, and writes nothing.
- **`sync`'s suggested fix for an old `MCP_STEERING_DIR` value now points at the installed package's docs** (`./node_modules/@3fn/core/governance`). For the value an earlier `init` wrote, it used to suggest `./governance`, a folder a consumer repo does not have. The "already has an entry" advice now names `attach`, not `init`.
- Container-Base and Input-Text referenced CSS variables that did not exist; they now resolve. The Input-Text-Password visibility toggle now has a hover state.
- Button-VerticalList-Item no longer throws when `.disabled` is set (the value is ignored), and Input-Radio-Base ignores a consumer-set `disabled` so it can no longer drop its value from form submission — consistent with 14.0.0's no-disabled-states rule.
- The published browser bundles (`designerpunk.esm.js`, `designerpunk.umd.js`) no longer embed the publishing machine's filesystem path in an internal module comment — a build-machine-identity leak with no functional effect on consumers, now removed.
- Removed four unused `Input-Text-*` browser-build files (`InputTextBase.browser.ts`, `InputTextEmail.browser.ts`, `InputTextPassword.browser.ts`, `InputTextPhoneNumber.browser.ts`, and their compiled `.js`/`.d.ts` output) from the package. They were never imported by the shipped bundle or by any documented usage path; removing them has no effect on any documented integration.

### Known limitations

- **Native (iOS/Android) onboarding is not supported in 15.0.0.** DesignerPunk's iOS and Android components read a theme surface that neither the package's token files nor your own `generate` emits in this version, so copying the native files does not yield a compiling target.
- **The iOS and Android token files do not emit theme-varying colours**, neither as constants nor through a theme type. Fourteen semantic colours are affected (among them `colorActionPrimary` and `colorStructureCanvas`), including the four listed under "Breaking"; ten of them were already missing in 14.1.0.
- **A theme you register in `designerpunk.config.ts` is not emitted yet, on any platform.** No `[data-theme="<name>"]` block is generated for web, and no theme structs or instances for iOS/Android. The web CSS carries DesignerPunk's base light/dark values and the built-in `data-theme="wcag"` block.
- **In a consumer repo, the application MCP's health check reports `degraded`**, with one "companion path not found: governance/Component-Family-….md" warning per component family. Component and token queries still answer; the companion docs are served by the docs MCP.
- **`--migrate-components` reports every copy as "cannot tell" when your registry access fails** (for example, an `.npmrc` pin to GitHub Packages with an expired token), including the version you have installed.
- **`sync --migrate-legacy` does not set up your personal note.** See step 4 of "Upgrading from 14.x".

### Upgrading from 14.x

1. `npm install @3fn/core@15.0.0`
2. `npx designerpunk sync` — review the report. Nothing is written before it prints.
3. `npx designerpunk sync --migrate-legacy --target=cc` (or `--target=kiro`), adding `--repair-tsconfig`, `--repair-npmrc` or `--migrate-components` if the report offers them. This converts the manifest, removes the copies you never edited, and generates the agent layer, in one run.
4. Create `.designerpunk/personal-note.local.md` (who you are and how you want to be worked with). Your agents read it every session; the migration does not create it.
5. Run `npx designerpunk generate`. If it stops on a component-token file an earlier `init` copied (`src/tokens/component/progress.ts` or `src/components/core/Button-Icon/buttonIcon.tokens.ts`), use the fix its message names: split the file's `defineComponentTokens()` into one call per family; or, for the `src/tokens/` file, replace it with the package's version and change its `'../../build/tokens'` import to `'@3fn/core/build'`; or, for an unedited `src/components/core/` copy, delete it.
6. Restart your agent session, then run `npx designerpunk sync` once more to review.
